# החוזה בין מסלול התפעול למסלול הממיר

זה הלב של "עבודה במקביל". שני המסלולים **לא חולקים קוד** — הם מדברים דרך הממשק הזה בלבד.
כל עוד החוזה יציב, אפשר לפתח את שניהם בו־זמנית בלי להתנגש.

```
soline-ops-app  ──(1) ORDX + מטא-דאטה──▶  ordx-pdp-converter
   (ניהול)      ◀──(2) DXF/PDP + סטטוס──   (המרה)
```

## כיוון 1: תפעול → ממיר (קליטת מדידה)
כשמודד מסיים מדידה, אפליקציית התפעול מפיקה **חבילת עבודה**:

```
job-<code>/
├─ measurement.ordx        ← קובץ המדידה מ-InnoDraw
├─ job.json                ← מטא-דאטה (ראה סכמה למטה)
└─ notes/                  ← צילומים/הערות שטח (אופציונלי)
```

`job.json` (החוזה — שדות אלה יציבים):
```json
{
  "code": "2026-0142",
  "client": { "name": "...", "phone": "...", "address": "..." },
  "surveyor": "...",
  "measuredAt": "2026-08-14T09:20:00Z",
  "type": "kitchen | electrical | full",
  "targets": ["dxf2d", "dxf3d", "pdp"]
}
```

הממיר קורא `measurement.ordx`, מריץ `soline_convert.js`, ומחזיר תוצרים.

## כיוון 2: ממיר → תפעול (תוצרים + סטטוס)
הממיר כותב לתיקיית התוצאה:
```
job-<code>/out/
├─ <code>.dxf              ← 2D
├─ <code>_3d.dxf           ← 3D
├─ <code>.pdp              ← Raumplan (כשמוכן)
└─ result.json            ← סטטוס: { "ok": true, "formats": [...], "warnings": [...] }
```

אפליקציית התפעול קוראת `result.json`, מעדכנת את סטטוס העבודה ל-"בעיבוד ✓", ומציגה את התוצרים במסך המסירה.

## נקודת החיבור בפועל (שלבים)
- **שלב 1 (עכשיו):** ידני — התפעול מייצא תיקיית `job-<code>/`, מישהו מריץ את הממיר, מחזיר `out/`. מוכיח את החוזה.
- **שלב 2:** תיקיית `inbox/` משותפת ב-Drive — התפעול שם חבילות, הממיר סורק ומעבד, מחזיר ל-`outbox/`.
- **שלב 3:** קריאת פונקציה/שירות ישירה (כשהממיר יהיה מודול נקרא).

## כללי ברזל
- **שדות `job.json` לא משתנים בלי לעדכן את שני ה-STATUS.** זה החוזה.
- הממיר אף פעם לא כותב לתוך state של התפעול, ולהפך — רק דרך הקבצים לעיל.
- שינוי בינארי (PDP) — רק דרך קוד הממיר, לא מהתפעול.
