# PDF_REPORT_SPEC — אפיון דו״ח-הפרויקט הסופי (PDF) של Soline

> **מטרה:** להגדיר, עמוד-אחר-עמוד וסעיף-אחר-סעיף, את **הדו״ח הסופי (PDF)** שמודד/משרד מפיק בסוף עבודה — הדליברבל שהנגר והמפעל מקבלים. עברית, RTL, לשון-זכר.
> **גישה:** משדרג את `PdfExporter` של CVSM (4 עמודים, אנגלית, `SheetKind = cover/plan/elevation`) לדו״ח **עשיר יותר בעברית**: כיסוי מלא של אלמנטים + מידות + ממצאי-התאמה (R1–R10) + הערות מסוננות-תפקיד + שדות-עריכה-במפעל.
> **שני מימושים משתפי-מבנה:** `PdfExporter` באפליקציה (Android/Kotlin) ו-`export_pdf.js` בממיר (Node). שניהם צורכים את **אותו מודל-אובייקט קנוני** (`.sol` / `ProjectSummary`).
> גרסה 1.0 · 2026-08-17 · יחידות מ״מ אלא אם צוין · מקורות: `NEW_PROJECT_FLOW.md`, `CVSM_EXPORT_CRACK.md §2.3`, `ProjectSummary.kt`, `ELEMENT_CATALOG_MERGED.md`, `FitEngine.kt`+`RulesExtra.kt`+`RoomValidator.kt`, `catalog/ElementCatalog.kt`, `data/{Entities,JobModel}.kt`.

## 0. עקרונות-על

1. **מקור-אמת יחיד.** ה-PDF אינו מחזיק דאטה משלו — הוא **רינדור** של מודל-האובייקט (`Project → Room → Wall → Accessory` + `Carpenter`+`JobEntity` + `FitDelta[]` + `FieldNote[]`). כל שדה בדו״ח ממופה למקור-נתונים (טבלת §14).
2. **RTL מלא.** כיוון-בסיס ימין-לשמאל; יישור-טקסט לימין; טבלאות נקראות מימין-לשמאל (עמודת `#` בקצה-ימין); מספרים ומידות מוצגים LTR בתוך תא RTL (bidi-isolation), כדי ש-`1200 מ״מ` לא יתהפך.
3. **מודד מפיק, מפעל ממשיך.** יש שדות-פתוחים (placeholders) שהמפעל ממלא/עורך אחרי-קבלה — עמודות "מידה-סופית" ו"הערת-מפעל" בטבלאות, ובלוק-הערות ייעודי. (המשך-העריכה של המפעל — דרישת Michael, כבר קיים ב-`ProjectSummary.kt`.)
4. **חובה מול רשות.** שדה חסר מוצג כ-`—` (מקף), לעולם לא כתא-ריק שנראה כמו באג. שדות-חובה שחסרים מסומנים בצבע-אזהרה (ראה §12 "שער-איכות").
5. **גודל-עמוד:** A4 (210×297 מ״מ). כותרת-עליונה/תחתונה קבועות בכל עמוד (§8). שוליים 15 מ״מ. עמודי תוכנית/חזית עשויים להסתובב ל-**Landscape** אם השרטוט רחב (כמו `PdfExportSettings` של CVSM).

## 2. עמוד תוכנית (Plan) — פר-חדר

**תפקיד:** מבט-על (top-down) של החדר: מצולע-הקירות עם מידות-אורך, זוויות-פינה, ומיקום כל אלמנט/בליטה בהיטל. זה מה שהנגר "רואה" את החדר.

### 2.1 פריסה
- **כותרת-עמוד:** `תוכנית — <שם-החדר>` (למשל `תוכנית — מטבח`). מיושר לימין.
- **אזור-שרטוט (מרכזי, ~70% מגובה-העמוד):**
  - מצולע-החדר מקווי-הקירות, מסובב ל-fit-to-page, עם רשת-ייחוס עדינה מאחור (Cream `#FBF4E6`).
  - כל **קיר**: קו אפור-כהה (Ink), עם תווית-מידה מקבילה לקיר, מחוץ למצולע: `2450` (מ״מ). מודד ידיעת LTR.
  - כל **פינה**: תווית-זווית קטנה בקשת: `90°` / `92.4°`. זווית ≠ 90° מודגשת בכתום (Orange) — קשורה ל-R3.
  - כל **אלמנט**: סמל-נקודה על הקיר במיקומו (`fromLeft` לאורך הקיר), בצבע-קטגוריה, עם מספר-הפניה (`①②③…`) שמפנה לטבלת-האלמנטים (§4). אלמנט עם **ממצא-התאמה BLOCK** מקבל טבעת-אדומה.
  - **חץ-צפון / כיוון-כניסה** בפינה, אם ידוע.
- **מקרא (Legend):** תיבה בפינה-שמאל-תחתית — צבע ↔ קטגוריה (חשמל / אינסטלציה / פתחים / מבנה / תאורה), + סמל ה-BLOCK.
- **קנה-מידה:** פס-סרגל גרפי (`0 ─ 500 ─ 1000 מ״מ`) + טקסט `קנ״מ 1:50` (מחושב מ-fit).

### 2.2 שדות מדויקים
| פריט | ערך | מקור |
|---|---|---|
| שם-החדר | `מטבח` | `RoomEntity.name` |
| מצולע-קירות | קו לכל קיר | `WallEntity.length` + `angle` (שרשור-וקטורי, כמו `RoomValidator.closureGapMm`) |
| תווית-אורך | `2450` | `WallEntity.length` |
| תווית-זווית | `90°` | `WallEntity.angle` |
| מיקום-אלמנט | נקודה על קיר | `AccessoryEntity.fromLeft` (+ שיוך `wallId`) |
| צבע/סמל-אלמנט | לפי קטגוריה | `AccessoryEntity.type` → `ElementCatalog.of(type).group` |
| מספר-הפניה | `①` | אינדקס-הרצה (משותף עם §4) |
| טבעת-BLOCK | טבעת-אדומה | קיים `FitDelta(severity=BLOCK, protrusionId=…)` |
| קנה-מידה | `1:50` | מחושב מגבולות-השרטוט מול גודל-העמוד |

> **הערה:** בהיעדר גאומטריית-קיר תקינה (חדר לא-סגור — `ROOM_NOT_CLOSED` מ-`RoomValidator`) התוכנית מרונדרת עם **פס-אזהרה** בראש: `⚠ החדר אינו סגור — פער X מ״מ`. השרטוט עדיין מוצג "פתוח".

## 3. עמודי חזית (Elevation) — פר-קיר

**תפקיד:** תצוגת-חזית (front view) של כל קיר בנפרד: הקיר כמלבן `אורך × גובה`, וכל האלמנטים עליו בגובהם-האמיתי מהרצפה, עם קווי-מידה. זה **הלב** של מדידת-מטבחים (CVSM §10). עמוד אחד לכל קיר שיש בו אלמנטים; קירות ריקים מקובצים לשורת-סיכום.

### 3.1 פריסה
- **כותרת-עמוד:** `חזית — <שם-חדר> · קיר <מספר>` (למשל `חזית — מטבח · קיר 2`).
- **מלבן-הקיר:** רוחב = `length`, גובה = `height`, fit-to-page. קו-רצפה תחתון מודגש (Ink עבה) עם תווית `0`. קו-תקרה עליון עם תווית-הגובה `2700`.
- **אלמנטים בחזית:** כל אלמנט מצויר כמלבן במיקומו (`fromLeft` ×  `fromBottom`), בגודלו (`width × height`), בצבע-קטגוריה שקוף-חלקית, עם התווית העברית והמספר `①`.
- **קווי-מידה (Dimension bands / `DimBand` בסגנון CVSM):**
  - **פס אופקי תחתון:** מרחקי-אלמנטים משמאל-הקיר (`fromLeft`) — לא-נערמים.
  - **פס אנכי (ימין):** גבהי-אלמנטים מהרצפה (`fromBottom`) — לרוב מרכז-האלמנט (measure_ref=center).
  - חיצים אדריכליים או ↔, לפי הגדרה.
- **מסגרת-הנקודות שנקלטה (captured frame):** אם הקיר נלכד כ**צורה** (`WallShapeCapture` — קיר לא-ישר/מדורג/קשתי), מצוירת צורת-הקיר האמיתית מ-N הנקודות שנלכדו, לא מלבן. אחרת — מלבן פשוט.
- **תווית ראש-קיר:** אם `wallTopStyle` ≠ ישר (משופע/גמלון) — מצויר הפרופיל.

### 3.2 שדות מדויקים
| פריט | ערך | מקור |
|---|---|---|
| מס׳-קיר | `קיר 2` | `WallEntity.idx + 1` |
| אורך-הקיר | `3600` | `WallEntity.length` |
| גובה-הקיר | `2700` | `WallEntity.height` |
| אלמנט (מלבן) | לפי מידות | `AccessoryEntity.{width,height}` |
| מיקום-אופקי | `fromLeft` | `AccessoryEntity.fromLeft` |
| גובה-מהרצפה | `fromBottom` | `AccessoryEntity.fromBottom` |
| תווית-אלמנט | `שקע כפול ②` | `ElementCatalog.of(type).he` + מספר-הפניה |
| קו-מידה-אופקי | `450 · 1200 · …` | `fromLeft` פר-אלמנט |
| קו-מידה-אנכי | `350 · 1150 · …` | `fromBottom` פר-אלמנט |
| צורת-קיר נלכדה | פוליגון | נקודות `WallShapeCapture` *(אם קיים)* |

> **חיווי-התנגשות בחזית:** אלמנט שיש עליו `FitDelta` מקבל מסגרת-צבע לפי חומרה — אדום (BLOCK) / כתום (WARN). מספרו מפנה לעמוד-הממצאים (§6). זה מחבר את החזית לבדיקת-ההתאמה.

## 6. ממצאי-התאמה (R1–R10)

**תפקיד:** רשימת ההתנגשויות/האזהרות שמנוע-ההתאמה מצא בין תכנון-הנגר (שכבה A) למדידה (שכבה B) — **לתשומת-לב הנגר/המפעל לפני חיתוך**. זה הבידול של Soline; אין לזה מקבילה ב-CVSM. מבוסס `FitDelta` מ-`FitEngine.kt`+`RulesExtra.kt`.

### 6.1 פריסה — כרטיסים מדורגים לפי חומרה (BLOCK קודם)
```
┌─ 🔴 חסימה · R4 · קיר 2 ───────────────────────────┐
│ התנגשות: צינור גז בולט 30 מ״מ אל גב הארון         │
│ "ארון בסיס 60" (מרווח-גב 0 מ״מ) — חורג 30 מ״מ      │
│ ► פתרון מוצע: פינוי-גב סביב הבליטה / הזזת-התשתית /  │
│   ביטול — טעון אישור                               │
│ אלמנט: ② · ארון: ארון בסיס 60                      │
└────────────────────────────────────────────────────┘
┌─ 🔶 אזהרה · R1 · קיר 3 ───────────────────────────┐
│ נשאר פער של 40 מ״מ בין השורה לקיר                  │
│ ► פתרון מוצע: להשלים במילואה/פילר ברוחב 40 מ״מ    │
└────────────────────────────────────────────────────┘
```

### 6.2 שדות-כרטיס
| שדה | מקור | הצגה |
|---|---|---|
| חומרה | `FitDelta.severity` | 🔴 חסימה (BLOCK) · 🔶 אזהרה (WARN) · 🔵 מידע (INFO) |
| קוד-חוק | `FitDelta.rule` | `R4` + שם-החוק העברי (טבלה למטה) |
| הודעה | `FitDelta.message` | הטקסט המלא שהמנוע הפיק (כבר בעברית) |
| פתרון מוצע | `FitDelta.suggestion` | `► פתרון מוצע: …` |
| קישור-אלמנט | `FitDelta.protrusionId` | מספר-הפניה `②` |
| קישור-ארון | `FitDelta.cabinetId` | שם-הארון |
| חריגה | `FitDelta.delta` | `חורג X מ״מ` |

### 6.3 מקרא-החוקים (מודפס בתחתית-העמוד)
| קוד | שם | מה בודק |
|---|---|---|
| R1 | שורה לא-נכנסת | Σ רוחבי-ארונות ≠ אורך-קיר → חוסר/עודף + מילואה |
| R2 | קיר לא-אנך | רוחב@עליון ≠ רוחב@תחתון |
| R3 | זווית-פינה סוטה | Angle ≠ 90° בפינה עם ≥2 יחידות |
| R4 | התנגשות-בליטה | עומק-בליטה > מרווח-גב-הארון בטווח-הגובה |
| R5 | חריגת-הנמכה | ארון-גבוה חורג את הנמכת-התקרה |
| R6 | חסימת-פתיחה | מעטפת-פתיחת דלת/מגירה חותכת שכן/קיר/מכשיר |
| R7 | מרווח-מכשיר | נישת-מכשיר < רוחב-מכשיר + מרווח-יצרן |
| R8 | קיזוז לא-מיושם | מידה "סופי" על קיר עם ריצוף/חיפוי עתידי |
| R9 | מפלס-רצפה | הפרש-מפלס בין קצוות → רגלי-פילוס/צוקל |
| R10 | נפח-פנימי תפוס | מגירות בארון עם סיפון/בלון/מסתור |

> **מצב "אין ממצאים":** אם `FitDelta[]` ריק — מוצג פס-ירוק: `✓ לא נמצאו התנגשויות-התאמה. כל האלמנטים נכנסים בתכנון.` (רק כשהריצה אכן בוצעה; אם אין תכנון-נגר טעון — `ℹ טרם הורץ מנוע-התאמה (אין שכבת-תכנון).`)

### 11.2 טיפוגרפיה
- **פונט:** משפחה עברית מובנית עם משקלים (Heebo / Assistant / Rubik — לעגן נכס-פונט ב-`assets/fonts`, כי `PdfExporter` חייב פונט-מוטמע ל-RTL תקין; ברירת-המחדל האנגלית של CVSM לא מספיקה).
- **היררכיה:** כותרת-שער 28pt bold · כותרת-עמוד 18pt bold Teal · כותרת-סעיף 14pt bold · גוף 11pt · תווית-משנה/כיתוב 9pt Muted · מידות-בשרטוט 8–9pt.
- **מספרים:** תמיד LTR מבודד (bidi-isolate) בתוך טקסט RTL.

### 11.3 RTL — כללי-ברזל
- `dir=rtl` ברמת-מסמך; יישור-בסיס ימין.
- טבלאות: עמודת `#` בקצה-**ימין**; זרימת-עמודות ימין→שמאל.
- אייקונים/חיצים "קדימה" מתהפכים (mirror) בהתאם.
- ערכים-מספריים ויחידות (`מ״מ`, `°`, `1:50`) עטופים ב-span-LTR.

### 11.4 חובה מול רשות — סיכום
- **חובה (הדו״ח לא מופק בלעדיהם):** שם-פרויקט, לקוח, נגר, כתובת, מס׳-עבודה, תאריך-מדידה, מודד, לפחות חדר-אחד עם קיר-אחד תקין.
- **רשות (מוצג `—` אם חסר):** טלפונים, אימייל, חברה, איש-קשר, עיר/מיקוד, דרכי-גישה, כתובת-משלוח, הערות, סטטוס-מידה פר-אלמנט, ראש-קיר.
- שדה-חובה-חסר → מסומן WarnAmber והסטטוס-בשער יורד ל-`חסר-פרטים`.

## 12. שער-איכות → סטטוס-הדו״ח

הדו״ח משקף את `RoomValidator` + `FitEngine`:
- קיים `ValidationIssue(BLOCK)` (חדר-לא-סגור / מידה-חסרה) → הסטטוס-בשער `דורש-בדיקה`, ופס-אזהרה אדום בתוכנית/טבלה הרלוונטית.
- קיים `FitDelta(BLOCK)` → סטטוס `דורש-בדיקה` + הקדמת עמוד-הממצאים (§10.2).
- רק `WARN`/`INFO` → סטטוס `הושלם` עם הערה.
- שדות-חובה-חסרים → `חסר-פרטים`.
- הכול נקי → `הושלם`.

## 15. הערת-מימוש — שני מקומות, אותו מבנה

מבנה-הדו״ח (הסעיפים 1–9, סדר-ההרכבה §10, המיפוי §14) **משותף** לשני מימושים, ששניהם צורכים את אותו מודל-אובייקט קנוני:

1. **`PdfExporter` באפליקציה (Android/Kotlin)** — משדרג את המחלקה הקיימת (בסגנון CVSM `PdfExporter$SheetKind`) מ-4 עמודים אנגליים ל-מבנה הזה: `SheetKind = cover / plan / elevation / elementsTable / wallsTable / findings / notes / signatures`. משתמש ב-`android.graphics.pdf.PdfDocument` + Paint-ים (כמו `textPaint`/`strokePaint`/`fillPaint`), פונט-עברי מוטמע, ו-`Layout`/`StaticLayout` עם `TextDirection=RTL`. הנתונים כבר מורכבים ב-`ProjectSummary.kt` — יש להרחיבו כמקור-הטקסט, ולהוסיף שכבת-רינדור-גרפית לתוכנית/חזית (שימוש-חוזר בקנבס `RoomPlanCanvas` / `ElevationScreen`).
2. **`export_pdf.js` בממיר (Node)** — מימוש-מקביל שקורא `.sol` ומפיק את **אותו** PDF (RTL-עברי). ספרייה מומלצת: `pdfkit` או `pdf-lib` עם פונט-עברי מוטמע + `bidi`/reshaping, או רינדור-HTML→PDF (`interactive_export` בסגנון bravh → print-to-PDF) לשיתוף-קוד עם מייצא-ה-HTML העתידי. נכנס לצינור-המייצאים לצד `export_ordx.js`/`export_dxf2d.js` (ר׳ `CVSM_EXPORT_CRACK §4.1`).

**עוגן-ההסכם:** `render(objectModel) → bytes`. אין המרות-ביניים; שינוי-שדה במודל מופיע אוטומטית בשני המימושים. זה מקנה **יתרון על CVSM**: RTL-עברי מלא, ממצאי-התאמה (R1–R10), הערות-מסוננות-תפקיד ושדות-עריכה-במפעל — כולם חסרים ב-`PdfExporter` האנגלי של CVSM.
