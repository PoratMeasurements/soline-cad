## 1. מה למדנו מצינור ה-Blender של Raumplan

הצינור המקצועי (`HAMMES Software RPW20` → Blender) עובד בשישה שלבים. כל שלב הוא שיעור
עבור Soline.

### 1.1 אתחול סצנה — `initscene.py`
```
render.engine = 'CYCLES';  cycles.device = 'GPU'
world.light_settings.use_ambient_occlusion = True;  ao_factor = 0.25–0.275
```
- פותח `empty.blend`, מנוע **Cycles** (path-tracing), GPU.
- **Ambient Occlusion** דלוק — זה מה שנותן עומק לפינות (הצללה רכה במפגשי-משטחים).
- טוען את `materials.blend` (ספריית-חומרים, ~54 טמפלטים) ומוסיף אובייקט **`SkyDome`** —
  תאורת-סביבה מבוססת-תמונה (image-based lighting). **אין מקורות-אור נקודתיים בסצנה
  עצמה** — הכל מהכיפה + AO. זו הסיבה שהתמונות נראות טבעיות.

### 1.2 חומרים — הליבה של "מוחשי"
כל חומר בסצנה נבנה מ**העתקת טמפלט** + הזרקת טקסטורה + כוונון shader (node-based Cycles):
```python
newmat = bpy.data.materials["DiffuseTexture"].copy()
newmat.node_tree.nodes["Image Texture"].image = load("...\עץ\...jpg")
newmat.node_tree.nodes['Glossy BSDF'].inputs[1].default_value  = 0.18   # roughness
newmat.node_tree.nodes['Diffuse BSDF'].inputs[1].default_value = 78
```
- טמפלטים שנצפו: `DiffuseTexture`, `MetallChromTextur`, `Oberflaeche_Variabel`,
  `GLAS_FENSTERGLAS` (IOR≈1.2), `Principled BSDF`.
- **המפתח:** חומר = **מפת-תמונה (albedo)** + **חספוס (roughness)** + **BSDF מבריק/מפוזר**.
  עץ, שיש (Dekton), כרום, נירוסטה, זכוכית — כולם אותו מבנה, טקסטורה שונה.
- ספריית הטקסטורות (`blender_textur\`, **386 JPG**) מסודרת לפי חומר:
  `עץ`, `אריחים`, `זכוכיות`, `מתכתי`, `משטחי עבודה`, `פורמיקות`, `צבעים`, `מכשירים`
  (מקררים/תנורים ממופתחי-תמונה), `אינפיניטי פורצלן`, `בלורן`, ועוד.
- טמפלטי-החומרים ב-`materials.blend` (מ-`BlenderMaterial.lst`) מכסים כל מה שדרוש:
  `HOLZ_MATT/LACK/GEBUERSTET/GEBEIZT` (עץ), `METALL_*` (כרום/אלו/פליז/נחושת/זהב/
  נירוסטה + גרסות מוברשות), `GLAS_FENSTERGLAS/TUERGLAS/CRYSTAL`, `KERAMIK`, `MAUER`
  (בנייה), `MATT/GLANZ/HOCHGLANZ_COLOR`, `AreaLight`.

### 1.3 גיאומטריה — `addKoerper(name, parent, V, F, N, TC, MAT)`
כל "Koerper" (גוף) הוא **פאון סגור** עם:
- `V` — קדקודים ב-**מטרים** (מ"מ/1000), ציר Z מעלה.
- `F` — פאות (quads / n-gons).
- `N` — **normals מפוצלים פר-קדקוד** (`normals_split_custom_set`) — זה מה שמבדיל בין
  קצה-חד (מזווה ארון) לבין משטח-חלק (גליל). קריטי לאיכות-הצללה.
- `TC` — **קואורדינטות-טקסטורה (UV) פר-loop** — ממפות את מפת-החומר על הפאה.
- `MAT` — שם-חומר (מהספרייה).
- הגופים מקובצים תחת empties-הורים (למשל `"EIR"`) — היררכיית-סצנה.

### 1.4 מצלמה — `set_camera.py`
```
camera.data.lens_unit = 'FOV';  angle = 1.047 rad (60°)
location/rotation_euler  (במטרים, XYZ euler);  clip 0.01–10000
```
פרספקטיבה 60°, ממוקמת בגובה-עין (~1.1–1.3 מ'), מכוונת לתוך החדר.

### 1.5 איכות-רינדור — `settings_good.py`
```
cycles.samples = 24 (square);  max_bounces = 64;  diffuse/glossy/transmission = 16
caustics on;  resolution 1920×1080
```
GI מלא. איכות-שיווק, אך **כבד** (שניות-דקות פר-פריים, GPU).

### 1.6 ייבוא-אביזרים — `import3d.py`
מייבא מודלי-מכשירים חיצוניים (`obj/3ds/dae/fbx/skp/dxf...`) → **Decimate** (הפחתת-פאות
עד `maxverts`) → מנרמל קנה-מידה → מייצא ל-KIF. כך מכניסים מקררים/תנורים אמיתיים.

**המסקנה לתכנון:** צינור "מוחשי" = **נפח סגור** (V/F) + **normals** + **UV** + **חומר
(תמונה+roughness+BSDF)** + **תאורת-סביבה+AO** + **מצלמת-פרספקטיבה**. שום שלב אינו קסם —
כולם ניתנים לשחזור, החלק שלנו רק חסר את ארבעת הראשונים.

## 2. מה יש לנו היום, ומה הפער

מקור: `src/export_dxf_pro.js` (+ `DXF_REFERENCE_STUDY.md`).

| רכיב | מצב היום ב-Soline | לרינדור-מוחשי צריך |
|---|---|---|
| **קירות** | `wallPrism()` — פריזמת 3DFACE (מרכז-קו + עובי + גובה). **כבר נפח מלא!** | להוסיף normals + חומר-טיח; לחורר פתחים |
| **רצפה/תקרה** | ❌ אין | מישור-רצפה + תקרה מ-bounding-box של הקירות |
| **ארונות** | ❌ אין (Soline ממדל תשתית, לא קרקסים) | נפחי-ארון — קיימים ב-**PDP כ-QUADER/HALBKREIS** (`STATUS.md`) |
| **אביזרים** | קומפוזיציית-קופסאות axis-aligned (SOCKET 30 פאות…) דרך INSERT | לעטוף בחומר (מתכת/פלסטיק); דיוק מספיק |
| **חלונות/דלתות** | קופסת-3DFACE על `Const_Windows/Doors` (מסגרת+זיגוג) | חומר-זכוכית שקוף לזיגוג |
| **חומרים** | ❌ שכבות DXF (צבע-ACI בלבד) | ספריית-PBR: עץ/שיש/מתכת/זכוכית/טיח |
| **normals** | ❌ (3DFACE שטוח) | חלק vs חד פר-משטח |
| **תאורה** | ❌ | hemisphere/HDR + key-light + AO |
| **מצלמה** | ❌ (VPORT דו-ממדי) | פרספקטיבה / איזומטרי, מסלול |

הבשורה: **הבסיס הגיאומטרי כבר נכון** — קירות הם כבר פריזמות-נפח, ולאביזרים יש מודל
מוצק. הפער הוא כמעט-כולו **שכבת-הצגה** (חומר+תאורה+מצלמה+רצפה), לא גיאומטריה חדשה.

## 3. מה הופך 3D ל"מוחשי" — עקרונות

לפי סדר-תרומה לאפקט, מהזול-והמשפיע ביותר:

1. **נפחים מלאים (לא מעטפות דקות).** קיר = תיבה בגובה+עובי אמיתיים; ארון = גוש; משטח =
   לוח. יש לנו קירות; חסרים רצפה/תקרה/ארונות. **זה לבדו מסלק את מראה-ה"קווים".**
2. **רצפה + תקרה.** מישור-רצפה מגדיר "חדר" ולוכד צל — קופץ מיד מ"שלד" ל"חלל".
3. **תאורה + Ambient Occlusion.** אור-סביבה (hemisphere/HDR) לחשיפה טבעית + אור-מפתח
   כיווני לצללים + AO להצללת-פינות. בלי זה הכל שטוח.
4. **חומרי PBR.** לכל משטח: `baseColor/albedo` (או טקסטורה) + `roughness` + `metalness`.
   עץ מט, שיש חלק-מעט-מבריק, כרום מתכתי-חלק, זכוכית שקופה. **מבחין בין "אפור" ל"מטבח".**
5. **פרופורציות ופרטים נכונים.** גבהים אמיתיים (קיר 2.7 מ', משטח 0.9 מ', ארון-גבוה
   2.2 מ'), עובי-קיר, מרווחי-פתחים — מגיעים ישר ממודל-האובייקט (`dimensions_mm`).
6. **מצלמה.** פרספקטיבה בגובה-עין ל"תחושת-עמידה בחדר"; איזומטרי ל"מבט-על טכני". שתיהן
   בקלות מ-OrbitControls.

## 4. אדריכלות מוצעת — חוזה אחד, שני מנועים

```
                      מודל-האובייקט של Soline
        (elements.json + symbols.json + placement + PDP-QUADER)
                              │
                     ┌────────┴────────┐
                     │  Scene Builder   │   ← נפחים: קירות/רצפה/תקרה/ארונות/אביזרים/פתחים
                     │  (SceneGraph)    │      + שיוך-חומר פר-אובייקט
                     └────────┬────────┘
                              │  glTF 2.0  (נפחים + PBR + היררכיה)   ← פורמט-החילוף
                 ┌────────────┴────────────┐
                 ▼                          ▼
     ┌───────────────────────┐   ┌──────────────────────────┐
     │  three.js / WebGL      │   │  Blender headless (Cycles)│
     │  אינטראקטיבי · offline │   │  סטילס פוטוריאליסטי · ענן │
     │  (POC כבר קיים)        │   │  ממחזר materials.blend    │
     └───────────────────────┘   └──────────────────────────┘
```

### 4.1 למה glTF כפורמט-החילוף
- נייטיב ל-three.js (`GLTFLoader`), נייטיב-ייבוא ב-Blender, תומך PBR (metallic-roughness),
  היררכיה, ומופעים (instancing — מתאים לאביזרים החוזרים, בדיוק כמו INSERT).
- **חוזה יחיד**: בונה-הסצנה מפיק glTF; אחר-כך אפשר לרנדר גם live וגם פוטוריאליסטי בלי
  לכתוב שתי צנרות.
- חלופה קלה יותר: מבנה-JSON פנימי משלנו + מפרש three.js. אבל glTF נותן חינם את גשר-Blender.

### 4.2 מנוע A — three.js / WebGL (מומלץ ראשון)
- **למה:** מיידי, אינטראקטיבי, **offline-first** (עֵקרון-Soline — three.js נשמר מקומית),
  רץ בכל דפדפן, אפס-שרת. נותן 90% מ"התחושה המוחשית" ב-5% מהמאמץ.
- **הצינור:** geometry (BufferGeometry) → mesh → `MeshStandardMaterial` (PBR) →
  `HemisphereLight`+`DirectionalLight`(+shadow) → `PerspectiveCamera`+`OrbitControls` →
  `WebGLRenderer` (ACES tone-mapping, sRGB, PCFSoftShadow).
- **מיפוי-צירים:** Soline ב-מ"מ, ציר-Y של התכנית=עומק. במציג:
  `worldX=x/1000`, `worldY=גובה/1000` (Y-up), `worldZ=-y/1000` (היפוך כמו `placement.js`).
- **מצב-כפול:** אותו viewer מציג גם "מוצלל" וגם "wireframe" (toggle) — מגשר בין המהנדס
  למעצב.

### 4.3 מנוע B — Blender headless / Cycles (בהמשך, לפוטוריאליזם)
- **למה:** לסטילס-שיווק ברמת-Raumplan (חומרים אמיתיים, GI, caustics, DOF).
- **איך, בלי לבנות מאפס:** מפיקים מ-Soline סקריפט-Python בסגנון `main.py` (סדרת
  `addKoerper` + הגדרות-חומר) **או** glTF, ומריצים
  `blender --background --python build_scene.py -- scene.gltf out.png`. ממחזרים את
  `initscene.py` (SkyDome+AO), את `materials.blend` (54 טמפלטים), ואת `settings_good.py`.
- **היכן לרוץ:** worker בענן/שרת (GPU), אסינכרוני — Soline שולח סצנה, מקבל JPG. לא
  בדפדפן. מתאים ל"הזמן הדמיה" (לא לתצוגה חיה).

### 4.4 החוזה עם מודל-האובייקט הקיים
בונה-הסצנה קורא **רק** את החוזה הקיים (`OBJECT_MODEL.md`) — לא משנה קוד-מייצא:
```
scene = { walls[], items[], openings[] }         // כמו sceneFromModel()
  wall  : { x1,y1,x2,y2, thick, height, exterior }
  item  : { name, category, x, y, z, rotation_deg, width, depth, height }
  open. : { layer, x, y, z, rotation_deg, width, height, depth }
  (+ cabinets[] בעתיד, מ-PDP QUADER/HALBKREIS)
```
`dimensions_mm` (W×D×H) + `placement` (x,y,z,rotation) הם כל מה שצריך לבנות נפח.
חוזה-הסקאלה (`symbol.frame=[1000,1000]`, קנה-מידה לפי W/H) כבר מבטיח מידות-אמת.

## 5. המציגים שנבנו — מה מוצג

- **`analysis/out/soline_3d_viewer.html`** — **המציג הראשי, OFFLINE לחלוטין**: טוען
  **קובץ PDP שלם של Raumplan** ומציג הכל מוצלל כמו ב-Raumplan — **קירות** (נפחים
  מלאים) + **תשתיות** (אביזרי MEP במיקום אמיתי) + **ארונות** (קופסאות W×D×H לפי קטלוג
  אלקינצ'ו). **מנוע-הרינדור מוטמע בקובץ** (WebGL גולמי, ~250 שורות, בלי three.js ובלי
  CDN) — עובד בלי אינטרנט. כולל: **חיתוך-קיר אוטומטי** (הקיר שבין המצלמה לחדר מוסתר),
  מצלמת-מסלול, wireframe, בורר-סצנות, ופאנל מצאי חי. שתי סצנות אמיתיות מוטמעות:
  `תשתיות.pdp` (קירות+תשתיות) ו-`2922.pdp` (ארונות). פירוט הנתונים ב-§8.
- **`analysis/out/soline_3d_viewer_poc.html`** — POC ראשוני (three.js/CDN, סצנה
  סינתטית) שמדגים את צינור-הרינדור המינימלי. (מוחלף ע"י המציג הראשי; נשמר כרפרנס.)

הפירוט הבא (§5.1) הוא של צינור-הרינדור העקרוני; המציג הראשי ממש אותו ב-WebGL גולמי.

מה הוא מדגים — הצינור המלא בקטן:
- **טעינת החוזה**: אותה סצנת-מטבח סינתטית של `export_dxf_pro.js` (4 קירות + 5 אביזרים +
  חלון), + מדגם ארונות/משטח (מייצג את QUADER של PDP).
- **בונה-נפחים**: קירות כתיבות (מרכז-קו+עובי+גובה, מסובבות לפי כיוון-הקיר), רצפה
  מ-bounding-box, ארונות/משטח כגושים, אביזרים כקופסאות-קטנות בהצבה (x,y,z,rot),
  חלון כלוח-זכוכית שקוף.
- **ספריית-חומרים** (`MAT`): טיח פנים/חוץ, רצפה, עץ, שיש, מתכת, פליז, פלסטיק, זכוכית —
  ממופתחים לפי `category` (גז→פליז, אינסטלציה→מתכת, חשמל→פלסטיק). מקבילים לשמות
  `materials.blend` (`HOLZ_*`, `MetallChrom`, `GLAS_FENSTERGLAS`).
- **תאורה**: `HemisphereLight` (שמיים/קרקע — מקביל ל-SkyDome) + `DirectionalLight` עם
  צל רך + ambient עדין. tone-mapping ACES, sRGB.
- **מצלמה**: פרספקטיבה 50° + `OrbitControls` (גרירה/זום); toggle למבט-איזומטרי.
- **מצב-כפול**: toggle wireframe / shaded / צללים / הצג-ארונות.

הערת-offline: ה-POC טוען three.js מ-CDN לנוחות-הדגמה. לפרודקשן — **לשמור three.js
מקומית** (עֵקרון-Soline). זה השינוי היחיד הדרוש לפני שילוב.

## 6. דרישות ל-Soline (מה לבנות בפועל)

### 6.1 ספריית-חומרים (Material Library)
טבלת-חומרים קטנה, keyed לפי `category`/סוג-משטח, כל ערך = `{ baseColor|texture,
roughness, metalness, opacity }`. מינימום מומלץ:
| חומר | שימוש | roughness / metalness |
|---|---|---|
| טיח (פנים/חוץ) | קירות | 0.95 / 0 |
| ריצוף | רצפה | 0.7 / 0 (טקסטורה: אריחים/פרקט) |
| עץ (מט/לכה) | ארונות | 0.5 / 0 (טקסטורה: `עץ\`) |
| שיש/דקטון | משטח-עבודה | 0.3 / 0.05 (טקסטורה: `משטחי עבודה\`) |
| נירוסטה/כרום | ברז, מכשירים | 0.3 / 0.9 |
| זכוכית | חלון, ויטרינה | 0.05 / 0, opacity 0.28 |
| פלסטיק לבן | פנלי-חשמל | 0.5 / 0 |
ניתן למחזר ישירות את **386 הטקסטורות** של Raumplan (`blender_textur\`) — כבר מסודרות
לפי חומר. ל-three.js: albedo + roughness + normal map.

### 6.2 גיאומטריה — גבהים ועובי (כבר במודל)
- **גובה-קיר + עובי-קיר**: קיים ב-`wall.dimensions` (`height`, `thick`). ברירות-מחדל
  2500–2700 מ"מ / 100 מ"מ. יש לוודא שנקראים למציג.
- **רצפה/תקרה**: נגזרים מ-bounding-box של הקירות. תקרה אופציונלית (בד"כ מוסתרת במבט).
- **מידות-אמת**: `dimensions_mm` פר-אובייקט — אין קנה-מידה קבוע (חוזה-הסקאלה).

### 6.3 ארונות מ-PDP
המקור לנפחי-הארון הוא **מודל-המעצב ב-PDP**: block#2 = מש-3D כ-**QUADER/HALBKREIS
float32 במסגרת מקומית (cm)** (`STATUS.md` §"מש 3D"). כשה-RE של PDP יבשיל, יש להוסיף
`cabinets[]` לחוזה-הסצנה (kind, x,y,z0, w,d,h, material) ולבנות מהם גושים — בדיוק כמו
במציג ה-POC. עד אז — ארונות-מדגם פרמטריים מ`dimensions_mm`.

### 6.4 פורמט-ייצוא לרינדור
- **live**: מבנה-סצנה פנימי (JSON) → three.js. (או glTF ל-`GLTFLoader`.)
- **פוטוריאליסטי**: **glTF 2.0** (מומלץ) או סקריפט-`addKoerper` Python ל-Blender.
- שמירת-מיפוי `category → material` כדי ששני המנועים יראו זהה.

## 7. המלצה + שלושת הצעדים הראשונים

**המלצת-צינור:** ללכת על **three.js/WebGL כמנוע-הראשי לתצוגה מוחשית אינטראקטיבית**
(offline-first, מיידי, זול), עם **glTF כפורמט-חילוף** ששומר פתוחה את הדלת ל-**Blender
headless** לרינדור-שיווק בהמשך. לא לבנות מנוע-רינדור משלנו; לא להתחיל מ-Blender (כבד
מדי לאיטרציה). הבסיס הגיאומטרי כבר קיים — משלימים שכבת-הצגה.

### צעד 1 — בונה-נפחים משותף (Scene → Meshes)
מודול `sceneToMeshes(scene)` שקורא את החוזה הקיים (`sceneFromModel()`) ומפיק:
קירות-תיבה (יש `wallPrism`), **רצפה+תקרה מ-bounding-box**, אביזרים-קופסה (יש), פתחים,
ו**ווים לארונות** (`cabinets[]`, בינתיים פרמטריים מ-`dimensions_mm`; בהמשך מ-PDP QUADER).
מוצא: BufferGeometry/glTF. *(מדגם עובד כבר ב-POC — לחלץ למודול.)*

### צעד 2 — שכבת-חומרים
טבלת-החומרים של §6.1 + פונקציית-מיפוי `materialFor(object)` (לפי `category`/סוג-משטח).
להתחיל עם צבעי-PBR שטוחים (roughness/metalness), ואז לחבר את טקסטורות-Raumplan
(`blender_textur\עץ|משטחי עבודה|מתכתי`) כ-albedo. מקביל-שמות ל-`materials.blend`.

### צעד 3 — לחווט את המציג לסצנה האמיתית + לשמור three.js מקומית
להחליף במציג את הסצנה-המוטמעת ב-`sceneFromModel(parseOrdxFile(...))` (קירות+אביזרים)
+ `sceneFromPdp(...)` (ארונות — §8), להוסיף `HemisphereLight+DirectionalLight+AO`
ומצלמת-מסלול (כבר קיים במציג), ו**לשמור three.js מקומית** (offline). התוצאה: "3D
מוחשי" חי מכל ORDX/PDP — הניצחון-המהיר. לאחר-מכן: ייצוא-glTF + worker-Blender לסטילס.

## 8. PDP → מציג: קריאת קובץ PDP שלם (קירות + תשתיות + ארונות)

מודול: **`src/readPdp.js`** (קריאה-בלבד; לא נוגע ב-`writePdp.js`/מייצאים אחרים).

### 8.0 שני פורמטי-PDP — זיהוי לפי header
- **Raumplan-native** (`header ffffff7f`) — קבצי-הפרויקט המלאים של Raumplan. קירות
  כ-**int32 mm**, תשתיות ברשומות-פריט קבועות-אורך, ארונות בקודי-קטלוג. `readPdp`
  מזהה (`isNativePdp`) ומריץ את `readNative`.
- **DR-legacy** (header אפסים) — ייצוא-מדידה ישן. מטופל במסלול-הישן (מצאי-מרקרים).

`readPdp` בוחר אוטומטית. **קובץ-הבדיקה `analysis/out/תשתיות.pdp` הוא native.**

### 8.0.1 מה הוצג מ-`תשתיות.pdp` (native, 171KB)
| רכיב | כמות | מקור-חילוץ |
|---|---|---|
| **קירות** | **11** | `detectWallGroups` (`walls.js`) — int32: קבוצה חיצונית (4 קירות, עובי 250) + פנימית (7 קירות, עובי 100) |
| **תשתיות (MEP)** | **22** נקודות `SUPP_FR` | רשומת-פריט stride 431B; מיקום X/Y int32 ב-**offset +133/+137** מהמרקר (מיקום-עולם אמיתי, מ"מ) |
| **ארונות** | 0 | הקובץ תשתיתי — `KORPUS`=0; `DKP60/DLB60` הם מילון-קטלוג מוטמע (×1), לא ארונות מוצבים |
| פרימיטיבים | QUADER×60, ZYLINDER×35, WUERFEL×11 | גליפי-3D של האביזרים |

**איתור-מיקום אוטומטי** (`findPosOffset`): במקום offset קשיח, סורק את הרשומה ובוחר
את השדה שבו **כל** הנקודות נופלות בתוך תיבת-הקירות ובעלות ערכים מובחנים — עמיד
לשינויי-פורמט. (ה-Z/גובה-התקנה עדיין לא מפוענח → אביזרים במציג בגובה-ברירת-מחדל 1100.)

### 8.1 מה חולץ מ-PDP אמיתי (מאומת על קורפוС טריו, ~290 קבצים)
- **זהות-עבודה**: שם/לקוח (ריצות-ASCII בראש הקובץ).
- **מצאי-קטלוג (BOM) של הארונות** — הסיגנל האמין: קודי-מאמר × כמות. דוגמאות שנמצאו
  בקבצים אמיתיים: `SO60` (בסיס 60), `KP60`/`LB60` (מודולי-בסיס), `IK363` (פינתי),
  `AP60`/`MARMOR01` (**משטח-עבודה**: Arbeitsplatte / שיש), `DOOR13L/R`,`TUERE##`
  (חזיתות/דלתות), `FILLER13` (פאנל-מילוי), `BFL01`. הפרסר ממפה כל קוד ל**סוג**
  (base / tall / wall / worktop / front) ולמידות-מודול-תקן (`CATALOG` ב-`readPdp.js`).
- **מצאי-פרימיטיבים**: `KORPUS` (גוף-ארון, רשומות **210 בייט** — תואם
  `DXF_REFERENCE_STUDY` "מש 3D 210B"), `QUADER`, `ZYLINDER`, `FENSTER`, `HALBKREIS`.
- **קירות**: ניסיון-קריאה מטבלת-int16 (`0xd4`) עם בדיקת-תקינות; **לא כללי** על-פני
  הקורפוС (הפורמט תלוי-מיקום), ולכן מקור-הקירות האמין למציג הוא ORDX (`parseOrdx`).

### 8.1.1 מיפוי קוד-ארון → קטלוג אלקינצ'ו (`resolveCatalog`)
מקור-הקטלוג: **`docs/elkincho_catalog.json`** (87 אלמנטים: סדרות `B9D/B9M/M9/...`,
קטגוריות בעברית, `width_cm`, מכשירים). קודי-ה-PDP קצרים (`SO60`,`KP60`,`AP60`,`IK363`)
ולרוב **שונים** מקודי-הקטלוג הפורמליים (`B9D\01\50R`). `resolveCatalog(code)` מגשר:
1. **רוחב** — הספרות בסוף הקוד = רוחב בס"מ (`SO60`→60ס"מ→600מ"מ; `AP60`→600).
2. **התאמת-קטלוג** — חיפוש לפי קוד-מדויק ואז לפי **סדרה** (`M9\05\100` → נמצא ב-JSON,
   קטגוריה "8. משטח שייש"). כשנמצא — הקטגוריה קובעת **סוג** (kind) והמידות התקניות.
3. **מיפוי קטגוריה→סוג+מידות** (`kindFromCategory`): "א.תחתון" → **base** (D600·H720·
   רגלית100); "עליון" → **wall** (D320·H720·תלוי1450); "משטח/שייש/דלפק" → **worktop**
   (D620·H40·גובה900); "מקרר/מקפיא/עמוד" → **tall** (D600·H2080).
4. **נפילה-לאחור היוריסטית** (`catalogFor`) לקודים שאינם בקטלוג, לפי תחילית: `AP/MARMOR`
   →משטח, `DOOR/TUERE/FILLER`→חזית (מדולג, לא נפח), `IK/ECK`→פינתי, `OB/OST`→עליון,
   `HS/HOCH`→גבוה, אחרת base. גובה נגזר מהקטגוריה/סוג; רוחב מהקוד.

כך כל קוד-ארון ב-PDP הופך לקופסת-נפח W×D×H עם סוג-חומר (עץ/שיש) למציג. **דוגמאות
שאומתו:** `M9\05\100`→worktop (התאמת-קטלוג); `SO60/KP60/LB60`→base 600מ"מ (סדרה);
`AP60`→worktop; `IK363`→פינתי. ב-`2922.pdp` (native): **69 ארונות** (63 base + 6
משטחים) נפרשו לאורך הקירות (מידות-מודול; מיקום מדויק פר-KORPUS — §8.2).

### 8.2 מה **לא** פוענח (תיעוד ישר, לא ניחוש)
- **מיקום+מידות מדויקים של כל KORPUS**: הרשומה בת 210 הבייטים פרמטרית-עמוקה (מסגרת
  מקומית + טבלאות טרנספורם/אינדקס), ולכן הארונות **נספרים ומזוהים** (קוד+סוג+מידת-מודול)
  אך לא מפוענחים גיאומטרית פר-רשומה. עד לפענוח — המציג **בונה את נפחי-הארונות
  ממידות-המודול התקניות** (לפי קוד-הקטלוג) ו**פורש אותם אוטומטית לאורך הקירות**
  (`autoLayoutCabinets`): שורת-בסיס + משטח רציף מעליה + יחידות-קיר.
- **offsets אוניברסליים**: `0xd2/0xd4/0x10c/0x120` של `writePdp.js` הם תלויי-תבנית
  (calibrated לתורם ספציפי) ואינם מכלילים — לכן קריאה מדורגת עם gate-תקינות.

### 8.3 API
```
readPdp(buf|path)         -> dispatch: native -> {format:'native', walls, items(תשתיות), cabinets, ...}
                                       legacy -> {inventory, cabinets, walls, wallsOk, ...}
sceneFromPdp(path, opts)  -> { walls, items, cabinets, _pdp{file,format,fixtureCount,catalog,...} }
resolveCatalog(code)      -> {kind, W,D,H,z0, name, series, catalogMatched}  // אלקינצ'ו + היוריסטיקה
isNativePdp(buf) / readNative(buf) / loadElkincho()
```
`sceneFromPdp` מזהה פורמט: ב-native מחזיר קירות+תשתיות אמיתיים מה-PDP; ב-legacy לוקח
אביזרים מ-`opts.items` (ORDX). `_pdp` נושא BOM+ספירות למקרא-המציג. **המציג טוען את
פלט-הפורמט הזה ישירות** (מוטמע כ-JSON) ומרנדר קירות/תשתיות/ארונות מוצללים, offline.

## 9. דו-כיווניות: PDP ↔ מציג ↔ ORDX

המטרה של Michael: **ממיר דו-כיווני** — לראות ולעבוד על הארונות המתוכננים ב-Raumplan.
זרימת-הנתונים המלאה:

```
   Raumplan .pdp                                             InnoDraw .ordx
   (ארונות+קירות)                                            (מדידה: קירות+תשתית)
        │                                                            │
   readPdp.js  ─┐                                          ┌─ parseOrdx.js
  (ארונות: BOM  │                                          │  (קירות+אביזרים,
   +סוג+מודול)  ▼                                          ▼   מאומת)
             ┌──────────────  חוזה-סצנה אחיד  ──────────────┐
             │  { walls[], items[](אביזרים), cabinets[] }    │
             └───────────────────┬───────────────────────────┘
                                 ▼
                   soline_3d_viewer.html  (three.js)
              קירות+ארונות+אביזרים · מוצלל · אינטראקטיבי · עריכה
                                 │
                 ┌───────────────┴────────────────┐
                 ▼ (עריכה → כתיבה חזרה)             ▼
          writePdp.js  (סצנה→PDP,                export_ordx.js / export_dxf_pro.js
          template-patch — קירות/אביזרים)        (סצנה→ORDX / DXF תוכנית+3D)
```

### 9.1 הכיוונים
1. **PDP → מציג (מומש עכשיו):** `readPdp.js` מחלץ את מצאי-הארונות + פרימיטיבים
   מ-Raumplan; `sceneFromPdp` בונה סצנה; המציג מציג אותה מוצללת. (ארונות = מ-PDP;
   קירות/אביזרים = מ-ORDX התואם, המקור האמין להם.)
2. **מציג → עריכה:** ב-three.js אפשר לבחור/להזיז/למחוק ארון (`OrbitControls`+raycast);
   הסצנה היא מבנה-JSON חי — עריכה = שינוי `cabinets[]`/`items[]`.
3. **מציג → PDP/ORDX (חזרה):** הכתיבה-חזרה קיימת חלקית — `writePdp.js` כותב קירות+
   מאפס-אביזרים בתבנית (template-patch, מאומת), ו-`export_ordx.js` מייצר ORDX.
   השלמת כתיבת-ארונות ל-PDP תלויה בפענוח רשומת-ה-KORPUS (§8.2) — צעד-המשך.

### 9.2 מה חסר לדו-כיווניות מלאה
- **פענוח גיאומטריית KORPUS** (210B) → מיקום+מידות אמיתיים פר-ארון (כרגע: BOM+פריסה).
- **כתיבת-ארונות ל-PDP** (הזרקת KORPUS/QUADER בקוד-קטלוג) — מעבר לכתיבת-הקירות הקיימת.
- **raycast-עריכה** במציג (בחירה/גרירה/הצמדה-לקיר) — תשתית-הסצנה כבר תומכת.

### 9.3 המלצה מעשית לצעד-הבא של הדו-כיווניות
לפני פענוח-KORPUS המלא (מאמץ-RE כבד), הערך-המיידי הוא **מסלול-קריאה+תצוגה+עריכה
על מבנה-הסצנה** (JSON): לקרוא PDP→BOM, להציג במציג, לתת ל-Michael לסדר/לתקן ארונות
ויזואלית, ולשמור את מבנה-הסצנה של Soline (לא PDP-חזרה בשלב ראשון). כתיבה-חזרה ל-PDP
נכנסת כשפענוח-הרשומה מבשיל — עד אז הפלט-החזרה הוא ORDX/DXF (כבר עובד) + סצנת-Soline.
