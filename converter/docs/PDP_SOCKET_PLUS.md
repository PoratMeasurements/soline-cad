## TL;DR (השורה-התחתונה)

"שקע+" **אינו** נושא גאומטריה-פנימית משלו, **אינו** קוד-סמל אחר, ו**אינו** רשומה באורך/מבנה שונה.
הוא **רשומת-173B זהה לשקע רגיל** — אותו `code=3`, אותה **יחידת-11-בייט** `[0x91,0x9c)` בדיוק
(`030012000000000e000000`) — הנבדלת ממנו **רק** ב:

1. **מחרוזת-הסוג** `@+0x09`: `+שקע` (`2b f9 f7 f2`) במקום `שקע` (`f9 f7 f2`).
2. **השלישייה-השנייה של המידות** `t2 @+0x7f`: **המידה-המותאמת**, בעוד `t1 @+0x79` נשאר **native**.

מכיוון שה-code+block זהים, האייקון שמצויר הוא **בדיוק אותו גליף-שקע** (code 3) — לכן "אייקון-נכון".
מכיוון ש-`t1` (הגליף-הרפרנס) נעול על native והמידה-המותאמת יושבת ב-`t2` בלבד, המידה-המותאמת
**אינה מעוותת** את הגליף — לכן "מידה-מותאמת + אייקון-נכון בו-זמנית".

**זהים-בייט (קריטי):**

## 2. המנגנון — מה בדיוק מאפשר "מידה-מותאמת + אייקון-נכון"

### שדה-המידות ברשומת-173B = **שתי שלישיות** [W,D,H] int16
- `t1 @0x79` = **גודל-הרפרנס/native של הגליף** (נועל את צורת-הסמל).
- `t2 @0x7f` = **הגודל-המצויר בפועל** (ה-footprint).

מפילוח 40 הסלוטים בבסיס-האב `wall4_oc40` (`analysis/out/socket_plus.json`), החוק **עקבי לחלוטין**:

| משפחה | דוגמאות | דפוס |
|---|---|---|
| **🔒 קבוע** | שקע, מפסק, ברז, גז, טלפון, אנטנה, ק.בקורת, מים-משולב, ביוב, צ.מים | **`t1 == t2`** (שניהם native) |
| **🎚️ משתנה** | דלת, חלון, ארגז-תריס, רדיאטור, מזגן, עמוד, ק.חשמל, תאורה | **`t1 != t2`** (t1=רפרנס, t2=מצויר) |
| **➕ וריאנט-"+"** | **+שקע, +מפסק, +טלפון** | **`t1 == native הרגיל`, `t2 = מותאם`** |

כלומר **"+X" = לקחת אלמנט-קבוע X והפוך אותו למשתנה**: משאירים `t1` על ה-native של X (הגליף לא זז),
ומשחררים את `t2` למידה-מותאמת. לכן הגליף (code של X) מצויר נכון, אך ה-footprint גדול/מותאם.

### הוכחת "t2 = המידה שלנו" (שני דגימי +שקע, לא אחד)
יש **שני** מופעי +שקע נבדלים, שניהם `code=3`, `t1=[150,10,120]`, `unit` זהה:

| מקור | t2 |
|---|---|
| בסיס-האב `wall4_oc40` slot#24 | **[500,0,500]** |
| קובץ-הבעלים export | **[800,0,600]** |

`t2` **משתנה** בין הדגימות בעוד `t1`+`code`+`unit` **נעולים** → `t2` הוא **הגודל-המצויר המשתנה**
(מה שהבעלים צייר), לא תכונה-קבועה של "+שקע". זו הראיה המכריעה שהמנגנון הוא **מידה-מותאמת אמיתית**.

### ההשערות שנבחנו ונדחו/אושרו (בבייטים)
- **(א) גאומטריה-פנימית שמניעה את האייקון** — ❌ **נדחתה**. בלוקי ה-`QUADER/HALBKREI/KP60/Kranz/Lichtblende/Normal`
  יושבים ב-`0x600+`, **הרבה אחרי** שתי רשומות-הפריט (שנגמרות ב-`0x26c`) — זהו **גוף-3D הסטנדרטי של
  ייצוא-DR** (`HALBKREI×2` = שתי כיפות-השקע, `Wall`, קופסאות-3D), **לא** מטען-פנימי ברשומה. האייקון
  מצויר מ-`code=3`, **בדיוק כמו שקע רגיל**.
- **(ב) code-סמל אחר / דגל parametric** — ❌ **נדחתה**. code=3 זהה, ויחידת-`[0x91,0x9c)` זהה-בייט לשקע.
  **אין** בייט ברשומה שמבדיל +שקע משקע מלבד ה-label ו-`t2`.
- **(ג) אורך/מבנה-רשומה שונה** — ❌ **נדחתה**. אותה רשומת-173B בדיוק.
- **(ד) t1 native + t2 מותאם** — ✅ **אושרה** (הפרק לעיל).

## 3. הכללה — האם ניתן לתת לכל התשתית שלנו מידה-מותאמת + אייקון-נכון

### מה מוכח ובטוח היום
לפליטת רשומת "שקע+" **אין צורך** ביחידת-סמל חדשה ו**אין צורך** ש-"+שקע" יהיה קיים-מראש בבסיס:
המנגנון הוא **עריכת שני שדות-בטוחים בלבד** על סלוט-שקע רגיל —

```
1) type-string @0x09  → "+שקע"        (label — Soline כבר עורך labels)
2) t2 @0x7f           → המידה שלנו     (t1 @0x79 נשאר native = הגליף נעול)
   [0x91,0x9c) לא-נגעים  → אין 921
```

**פרוטוטייפ מאומת (`analysis/decode_socket_plus.js`):** לקחתי סלוט-שקע רגיל מבסיס-האב, כתבתי
label=`+שקע` + `t2=[500,0,500]`, ותו-לא. התוצאה:
- `unitUntouched: true` (אין 921), `t1Preserved: true` (גליף נעול),
- **`labelMatches / t2Matches / unitMatches` מול ה-+שקע ה-native האמיתי: כולם `true`**,
- הדיפים-הנותרים מול ה-+שקע ה-native הם **רק** שם-משני (`0x33+`) ומיקום (`0x85-0x8a`) — לעולם לא `[0x91,0x9c)`.

כלומר **פליטת "+שקע" ניתנת-להזרקה על כל בסיס שכבר יש בו שקע (code 3)** — זה 100% מהבסיסים הרלוונטיים,
דרך שדות-העריכה הבטוחים הקיימים. **אין תלות בבסיס-אב שמכיל +שקע.**

### מימוש ב-`writePdpDR.js` — מומש (2026-08-25) ✅
מצב-➕ מומש כהרחבת דיכוטומיית 🔒/🎚️ הקיימת למצב-שלישי (t1-native + t2-מותאם):

1. **`SIZE_PLUS` + `isSizePlus()`** — סט הטיפוסים "+"-capable: `שקע, מפסק, טלפון, מזגן, חור איורור`.
   (`SIZE_PLUS_VERIFIED` = `{שקע}` בלבד — היחיד המאומת מול דגימת-בעלים אמיתית.)
2. **`editSlotInPlace` — עץ-החלטה (opt-in ע"י `opts.emitPlus`):**
   - **➕ "+X"** — `isSizePlus(type) && emitPlus && מידה-מותאמת` (≠ native-GT) → משמר `t1 @0x79`
     native (הגליף נעול), כותב `t2 @0x7f` = המידה-שלנו `[W,D,H]`, ה-label יוצא `+X`,
     **לא נוגע** ב-`[0x91,0x9c)`.
   - **🔒 קבוע** — `(isSizePlus && emitPlus && מידה=native/חסרה) || isSizeFixed(type)` → משמר את
     בייטי-הגודל ה-native (`[0x79,0x85)`).
   - **🎚️ משתנה** — כל השאר → כותב `[W,D,H]` לשתי השלישיות, כמו היום.
   - `emitPlus` **כבוי כברירת-מחדל** ⇒ אף נתיב-המרה קיים לא משתנה; טיפוסי-SIZE_PLUS ללא-emitPlus
     מתנהגים כרגיל (🔒 אם ב-SIZE_FIXED, אחרת 🎚️).
3. **מיקום** נכתב כרגיל (world = stored+20000, חיובי). tally `plusEmitted` + `plusReport` מוחזרים.
4. `verifyPropertyBlocks` הקיים מאמת ש-`[0x91,0x9c)`+terminator זהים-בייט + world-חיובי — תופס רגרסיה.

### מה **מוכח** לעומת מה **סביר-אך-לא-מוכח** (סטנדרט-האימות של המימוש)
המימוש (`SIZE_PLUS` / `SIZE_PLUS_VERIFIED`) נוקט סטנדרט-אימות **מחמיר**: "מאומת" = יש דגימת-בעלים אמיתית
שמוכיחה ש-`t2` מקבל מידה-מותאמת **שרירותית שלנו** (שני מופעים נבדלים לפחות).
- **מאומת-בייט (טיפוס אחד): שקע** — שני +שקע נבדלים (בסיס `t2=[500,0,500]`, ייצוא-בעלים `t2=[800,0,600]`)
  מוכיחים ש-`t2` משתנה בעוד `t1/code/unit` נעולים. נפלט **בייט-זהה** (label/t1/unit) לרשומת-הבעלים.
- **בסט-`SIZE_PLUS` אך ⚠️ PENDING דגימה (מפסק/טלפון/מזגן/חור-איורור):** לבסיס-האב יש native
  `+מפסק/+טלפון` (slots #21/#29) והמבנה `t1/t2` **סביר-מאוד-זהה**, אך **אין דגימת-בעלים** שמוכיחה ש-`t2`
  שלהם מקבל מידה **שרירותית** (רק מופע-native יחיד לכל אחד — ייתכן ש-`t2` קבוע כתכונת-הווריאנט).
  לכן ממומשים אך מסומנים PENDING עד דגימה.
- **מחוץ-לסט (גז וכו'):** גז — **אין** לו "+". שאר התשתית (ברז/מים-משולב/אנטנה/ק.בקורת…): מכיוון שאין **שום בייט** ב-`[0x91,0x9c)`
  שמבדיל +שקע משקע, סביר שהתנהגות ה-`t1/t2` היא **גנרית לכל code** — כלומר גם `+גז`/`+ברז` יעבדו באותה
  צורה. **אך זה טרם נצפה.** ייתכן ש-InnoDraw מאפשר את התנהגות-ההגדלה רק לטיפוסים שלהם הוא מגדיר וריאנט-"+"
  בספרייה-הפנימית שלו (SocketEx/SwitchEx/PhoneEx). היחידה-הזהה **טוענת** לגנריות, אך רק load-test יכריע.

## 4. התלות/סיכון שנותר (מדויק)

**הדבר היחיד שלא-מוכח:** האם Raumplan יצייר "אייקון-נכון + מידה-מותאמת" עבור וריאנט-"+" של טיפוס
ש-InnoDraw **לא** משלח לו "+" מובנה (גז/ברז/מים-משולב/אנטנה/ק.בקורת). ראיה-בבייטים תומכת בגנריות
(יחידת-`[0x91,0x9c)` זהה בין X ל-+X — אין דגל-מבחין), אבל היא **אינדיקציה, לא הוכחה**.

**דגימה אחת מכריעה את זה:** שהבעלים יצייר ב-Raumplan **"+גז" (או כל טיפוס-MEP אחר) בגודל לא-סטנדרטי**
ויְיצא כ-`.pdp` DR. אם התוצאה = code של גז (6), `t1` native, `t2` = הגודל-שצויר, ואייקון-נכון בטעינה →
המנגנון **גנרי מוכח** ונוכל לפתוח מידה-מותאמת לכל התשתית. אם Raumplan מתעלם/מעוות → ההגדלה מוגבלת
ל-{שקע,מפסק,טלפון} ש-InnoDraw כבר תומך בהם.

**מה שכן מוכן היום ללא כל תלות:** פליטת `+שקע/+מפסק/+טלפון` עם מידה-מותאמת, בייט-זהה לרשומות-הבעלים,
דרך עריכת label+t2 בלבד (אין 921, אין אלמנט-ספרייה חדש).
