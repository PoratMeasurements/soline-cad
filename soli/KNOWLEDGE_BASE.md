# KNOWLEDGE_BASE — הליבה של סולי

> זהו מאגר-הידע שסולי עונה ממנו. הכל מקורקע בתיעוד-המערכת של Soline (`../converter/docs/`). כשעובדה כאן מתנגשת עם קובץ-פרויקט אמיתי — **קובץ-הפרויקט קובע**, וסולי אומרת מה היא רואה בו.

---

## 0. איך כל החבילה מתחברת (התמונה הגדולה)

הצינור של Soline:
```
מודד בשטח (אפליקציית app-measure, 3 מדי-לייזר, offline)
        │  כותב
        ▼
   קובץ  .sol   ← מקור-האמת של הפרויקט (קונטיינר אחד)
        │  נכנס ל
        ▼
   הממיר  soline_convert.js
        │  מייצר בפקודה אחת
        ▼
 ┌─────────────┬──────────┬───────────┬───────────┬──────────┬───────────┐
 │   .ordx     │   .pdp   │  _2d.dxf  │  _3d.dxf  │   .pdf   │ _report.html │
 │ XML-מדידה   │ Raumplan │ תכנית-CAD │ נפח-CAD   │ דו"ח-נגר │ דו"ח-אינטראקטיבי│
 └─────────────┴──────────┴───────────┴───────────┴──────────┴───────────┘
```

**עיקרון-על:** כל ששת-הפורמטים נגזרים מ**אותו מודל-אובייקט קנוני אחד**. אותו קיר, אותו פתח, אותה מידה — פשוט מוצגים בשפה שכל תוכנה מבינה. לכן:
- **המידות זהות בכל הקבצים** (הכל במ"מ). אם ראית 909 בדו"ח, זה אותו 909 ב-DXF וב-PDP.
- **אין קובץ "יותר-נכון" מבחינת-מספרים** — יש קובץ **קריא-יותר לאדם** (הדו"ח) וקבצים **מדויקים-לתוכנה** (CAD/PDP). המספר אותו מספר.
- הבדל יחיד: **גאומטריית-מיקום ב-PDP** מדויקת מלאה רק בחלק מהמקרים (ראה §3); לכל השאר ה-PDP נכון-במבנה והמיקום להמחשה. למידות-אמת — הדו"ח וה-DXF.

**מהו "המודל הקנוני"** (רקע לנגר סקרן): לכל אלמנט יש זהות (עברית+אנגלית+קטגוריה), מידות W×D×H במ"מ, גובה-התקנה מהרצפה, וסמל-2D מנורמל. הכל נמדד בשטח ומאוחסן ב-`.sol`.

## 1. קובץ ה-`.sol` — מקור-האמת של Soline

| | |
|---|---|
| **מה זה** | קובץ-הפרויקט המקורי של Soline. **קונטיינר** אחד שאורז את כל המדידה: המבנה (manifest), המטא-דאטה (מי מדד, מתי, מספר-עבודה), וקובצי-החדרים. טכנית זהו קובץ **ZIP** עם סיומת `.sol`. |
| **במה פותחים** | **אין תוכנה חיצונית שפותחת `.sol` ישירות** — זה פורמט-הבית של Soline. הוא נועד לצינור-הממיר, לא לנגר. אם ממש רוצים להציץ: אפשר לשנות סיומת ל-`.zip` ולפתוח, אבל **אין צורך** — כל מה שבפנים כבר יוצא כ-6 הפורמטים הקריאים. |
| **למה הנגר צריך אותו** | בדרך-כלל **לא ישירות**. זהו הקובץ שמייצר את כל השאר; שומרים אותו כ**גיבוי-אב** של הפרויקט. אם משהו בחבילה חסר או נראה שגוי — מ-`.sol` אפשר להפיק מחדש את כל הפורמטים. |
| **מה מכיל בפנים** | `manifest.json` (מבנה), `meta.json` (פרטי-עבודה), `measured/room-*.json` (חדר לכל קובץ: קירות, אביזרים, פתחים). לפעמים גם `measured/source.ordx` מוטמע (מדידת-מקור מלאה) ו-`planning/cabinets.json` (תכנון-ארונות, אם נעשה). |
| **שאלות נפוצות** | "פתחתי ולא ראיתי כלום" → זה ZIP, לא מסמך. "איזה קובץ שולחים חזרה ל-Soline לתיקון?" → את ה-`.sol`, זה המקור. |
| **מלכודות** | אל תערוך את ה-`.sol` ביד — הוא נכתב ע"י האפליקציה בפורמט מדויק. **שמור אותו**; אל תמחק אחרי שהוצאת את שאר-הקבצים. |

## 2. קובץ ה-`.ordx` — XML-המדידה התעשייתי

| | |
|---|---|
| **מה זה** | פורמט **ORDX** (CV ORDX Order XML) של תוכנת **InnoDraw** — תקן-תעשייה למדידות-מטבח. XML קריא-מכונה שמתאר את החדר: קירות (נקודות-קצה, גובה, עובי, סוקל), ואביזרים/פתחים (שקעים, חשמל, חלונות, דלתות, הנמכות-תקרה) עם מידות ומיקום. |
| **במה פותחים** | תוכנות-תכנון-מטבח שתומכות ב-ORDX (משפחת-InnoDraw וכלים תואמים). כ-XML — נפתח גם ב**כל עורך-טקסט**/דפדפן לצפייה, אבל זה לא נועד לקריאה-אנושית שוטפת. |
| **למה הנגר צריך אותו** | אם בית-המלאכה עובד עם תוכנת-תכנון תואמת-ORDX — זהו **קובץ-הייבוא**: טוענים אותו והחדר קם בתוכנה עם כל המידות. אם לא — אין צורך; הדו"ח וה-DXF מספיקים. |
| **מה יש בפנים (מבנה)** | `job` (שם/תיאור-עבודה) · `customer`/`shipTo` · `rooms[]` → כל חדר `walls[]` → כל קיר: `position` (startX,startY,angle,endX,endY), `dimensions` (length,height,soffit,thick), `fixtures[]` (שקעים/חשמל), `furnishings[]` (חלונות/דלתות/הנמכות). מידות: **width,height,depth** לכל פריט. |
| **שאלות נפוצות** | "מה ההבדל בין ORDX ל-PDP?" → ORDX הוא המדידה-הגולמית (XML, תעשייתי-פתוח); PDP הוא הפלט לתוכנת-Raumplan הספציפית. שניהם אותו חדר. "ORDX פותח באוטוקאד?" → לא ישירות; לאוטוקאד השתמש ב-DXF. |
| **מלכודות** | ORDX הוא **XML** — אל תערוך ידנית אם אינך יודע מה אתה עושה; תג-שבור מפיל את הטעינה. |

## 3. קובץ ה-`.pdp` — התכנית ל-Raumplan

| | |
|---|---|
| **מה זה** | פורמט **PDP** — הפורמט הבינארי של **Raumplan for Windows IV**, תוכנת-תכנון-מטבחים. מכיל את הקירות (גאומטריה+טופולוגיה) ואת האביזרים/פתחים כרשומות-בינאריות + מודל-תלת-ממד. Raumplan משחזר את התלת-ממד מהנתונים בטעינה. |
| **במה פותחים** | **Raumplan for Windows IV** (ומהדורות-תואמות). זו התוכנה היחידה שקוראת PDP. |
| **למה הנגר צריך אותו** | אם בית-המלאכה מתכנן ב-Raumplan — טוענים את ה-PDP והחדר קם שם מוכן-לתכנון (ארונות, חזיתות, חיתוכים בתוך Raumplan). |
| **מה חשוב לדעת על הדיוק** | הקירות והמידות ב-PDP **נכונים**. **מיקום-האביזרים** (שקע/דלת על הקיר) מדויק-גאומטרית באופן-מלא רק בחלק-מהמקרים; באחרים הרשומה **תקינה-במבנה** והמיקום **להמחשה**. ⚠️ **לכן: את המידות-המחייבות לייצור קח מהדו"ח ומ-DXF, לא מהמיקום-הגרפי ב-PDP.** |
| **שאלות נפוצות** | "טענתי ולא נפתח" → ודא **גרסת-Raumplan תואמת**; PDP רגיש-לגרסה. "השקע במקום קצת שונה מהמדידה" → ייתכן; המיקום ב-PDP להמחשה. המידה-המחייבת בדו"ח. |
| **מלכודות** | 1) **בדוק-טעינה לפני שאתה בונה עליו** — טען ב-Raumplan וּודא שהחדר עלה נכון. 2) אל **תשמור-מחדש** מעל קובץ-המקור לפני שוידאת שנטען כמו-שצריך. 3) גרסת-תוכנה לא-תואמת = לא-ייטען. |

## 4. קובץ ה-`_2d.dxf` — תכנית-הרצפה ל-CAD

| | |
|---|---|
| **מה זה** | **DXF דו-ממד** (AutoCAD Exchange, גרסת AC1015) — **תכנית-רצפה** של החדר: קירות (קווים), פתחים ואביזרים כ**סמלים** (בלוקים), מידות, ומקרא בעברית. שכבות מסודרות לפי-קטגוריה. |
| **במה פותחים** | **כל תוכנת-CAD**: AutoCAD, כמו-גם חלופות (LibreCAD, DraftSight, BricsCAD, nanoCAD ועוד). זהו פורמט-חילופין אוניברסלי. |
| **למה הנגר צריך אותו** | זו **תכנית-העבודה השטוחה**: מכאן מודדים מרחקים, מתכננים את **מהלך-הארונות** לאורך-הקיר, רואים איפה יושבים חלון/דלת/שקע/פינה. אפשר לתכנן עליה, למדוד, ולהוציא ממנה חיתוכים. |
| **מה יש בו** | קירות כקווים לפי-מידות-אמת · פתחים/דלתות עם **קשת-פתיחה** (כיוון-ציר לפי צד-ציר וכיוון-פתיחה) · משקוף מצויר לפי עובי-משקוף/חשפה · שקעים/חשמל כסמלים על-הקיר · **מידות** ומקרא-עברי. הכל וקטורי ובמ"מ. |
| **שאלות נפוצות** | "העברית יוצאת ריבועים/????" → נושא-קידוד ידוע; אם קרה, פתח ב-CAD שתומך-עברית או פנה ל-Soline. "אין לי אוטוקאד" → LibreCAD חינמי פותח DXF. "המידות ריקות" → ודא ששכבת-המידות דלוקה. |
| **מלכודות** | 1) עבוד ב**מ"מ** (יחידת-הקובץ). 2) הפתח שמצויר הוא **הפתח הנטו** — עובי-המשקוף בנפרד. 3) קשת-הפתיחה מראה **כיוון**, לא רדיוס-מחייב. |

## 5. קובץ ה-`_3d.dxf` — מודל-הנפח ל-CAD

| | |
|---|---|
| **מה זה** | **DXF תלת-ממד** — מודל-נפח של החדר: **קירות מלאים** + כל אלמנט כ**תיבה W×D×H** (משטחי-3DFACE), עם **חללי-פתח אמיתיים** בקירות (חלון/דלת "חתוכים" בקיר בגובה-הסף הנכון) ותוויות-עברית. שכבות לפי-קטגוריה. |
| **במה פותחים** | **כל תוכנת-CAD תלת-ממדית**: AutoCAD, ורוב חלופות-ה-CAD. |
| **למה הנגר צריך אותו** | **הדמיה-מרחבית** של החדר: לראות גבהים, איך פתח יושב בקיר, איפה בליטות/עמודים/הנמכות מפריעות לארון. טוב לבדיקת-התנגשויות ולהצגה-ללקוח. |
| **מה יש בו** | כל אלמנט = תיבה בגודלו-האמיתי (רוחב×עומק×גובה), ממורכזת על נקודת-ההצבה, הבליטה (D) יוצאת מהקיר. קירות בגובה-אמת. פתחים = חורים-אמיתיים בקיר. |
| **שאלות נפוצות** | "למה יש שני קובצי-DXF?" → דו-ממד = תכנית-שטוחה-לתכנון; תלת-ממד = נפח-להדמיה. אותו חדר, שני-מבטים. "האלמנטים תיבות ולא בפירוט" → כן, ברירת-המחדל היא תיבת-נפח לכל אלמנט (מספיק לבדיקת-מקום/התנגשות). |
| **מלכודות** | זהו מודל-**המצב-הקיים** (החדר כפי-שנמדד) — לא מודל-הרהיט-שלך. את הרהיט אתה מתכנן; זה הבמה שהוא נכנס אליה. |

## 6. קובץ ה-`.pdf` — דו"ח-הנגר המודפס

|---|---|

| **למה הנגר צריך אותו** | **זה נקודת-ההתחלה של רוב-הנגרים.** כאן, בעברית ובמבט-אחד: שער-פרויקט, **תכנית לכל חדר**, **חזית לכל קיר**, **טבלת-מידות**, **טבלת-אלמנטים** (כל דלת/חלון/שקע עם מידותיו), **ממצאים** (בעיות/אזהרות), והערות. |
| **מה יש בו** | שער · תכנית-רצפה (וקטורית) פר-חדר · חזית פר-קיר · טבלת-מידות · טבלת-אלמנטים (מס'/סוג/רוחב×גובה/משקוף/כיוון/סף) · ממצאי-בדיקה R1–R10 · הערות (מסוננות-לפי-תפקיד) + בלוק-הערות-למפעל. אולי עמוד-חתימות. |
| **דבר-נחמד לדעת** | השרטוטים בדו"ח הם **וקטוריים אמיתיים** (SVG→PDF), לא תמונה — הקווים נקיים, וניתן אפילו להמיר-בחזרה ל-DXF בקלות אם צריך. |
| **שאלות נפוצות** | "איפה כל המידות במקום-אחד?" → **טבלת-המידות + טבלת-האלמנטים** בדו"ח. "מה זה R1–R10?" → בדיקות-שלמות-אוטומטיות של Soline (למשל סתירות-מידה, פתח-חסר-נתון). "היכן הערות-מיוחדות?" → סעיף-ההערות + בלוק-המפעל. |
| **מלכודות** | הדו"ח משקף את **מה שנמדד**. אם שדה מסוים ריק/"—" — פירושו **לא-נמדד**, לא "אפס". במקרה כזה — לוודא מול המודד לפני-ייצור. |

## 8. זרימת-התחלה מומלצת (Getting Started לנגר)

**קיבלת חבילה מ-Soline? כך מתחילים:**

1. **פתח את ה-`.pdf` (או ה-`_report.html` בדפדפן).** קרא את השער, טבלת-המידות, וטבלת-האלמנטים. עכשיו יש לך תמונה מלאה של החדר בעברית.
2. **עבור לסעיף-הממצאים (R1–R10) וההערות.** יש אזהרה? פתח-חסר-נתון? סתירת-מידה? זה מה שיעצור אותך אח"כ — טפל בו עכשיו (למשל: לבקש השלמת-מדידה).
3. **החלט איך אתה מתכנן:**
   - מתכנן ב-**Raumplan** → טען את ה-`.pdp` (ודא-טעינה קודם).
   - מתכנן ב-**תוכנת-מטבח תואמת-ORDX** → יבא את ה-`.ordx`.
   - מתכנן ב-**CAD כללי** (אוטוקאד/LibreCAD) → פתח את ה-`_2d.dxf` לתכנית ואת ה-`_3d.dxf` להדמיה.
   - עובד **מהנייר** → הדפס את ה-PDF ותכנן ידנית מטבלת-המידות והחזיתות.
4. **תכנן את מהלך-הארונות** על-גבי התכנית (DXF/Raumplan). *(תכנון-מטבח מלא — חלוקת-מודולים, חיתוכים, ניצול-לוח — הוא מודול-אח נפרד; ראה §10.)*
5. **שמור את ה-`.sol` כגיבוי-אב.** אם צריך תיקון/מדידה-נוספת — הוא הקובץ שחוזר ל-Soline.

**כלל-אצבע:** *מספרים → מהדו"ח וה-DXF. תכנון-חזותי → Raumplan/CAD. מקור/גיבוי → ה-.sol.*

## 9א. מתי לוודא לפני-שממשיכים (כללי-זהירות לנגר)

סולי כלי-עזר טוב, אבל האחריות המקצועית בבית-המלאכה נשארת של הנגר. שלוש נקודות שבהן **תמיד מוודאים**:

1. **מידה חסרה ≠ מידה-בערך.** שדה ריק/"—" בדו"ח פירושו **לא-נמדד**. סולי לא תשלים אותו בניחוש, וגם הנגר לא צריך — בקשת השלמת-מדידה מהמודד זולה בהרבה מלוח שנחתך לא-נכון.
2. **"מרחק/גובה תקני" — לא מהזיכרון.** אם צריך מספר-תקן (מרווח-בטיחות, גובה-עבודה, מרחק-מנקודת-מים) — זו החלטה מקצועית של הנגר לפי התקן-הישראלי הרלוונטי, לא מספר שסולי שולפת. המידה המחייבת בפרויקט = **מה שנמדד**, מהדו"ח/DXF.
3. **חישוב-כמויות — בקרה-כפולה.** לספירת-יחידות, אורך-מצטבר או ניצול-לוח — עושים בקרה עצמאית (מחשבון/מדידה חוזרת) לפני חיתוך או הזמנת-חומר. אף חישוב לא הבסיס-היחיד להזמנה שעולה כסף.

**פרטיות:** אם סולי רצה מול שירות-בענן — אין צורך להדביק פרטים-מזהים של הלקוח (כתובת, ת"ז, טלפון, סכומי-חוזה). המידות והממצאים מספיקים לעבודה.

## 9ב. צילום-מסך כקלט (העיניים של סולי)

לפעמים מהיר יותר **להראות** מאשר לתאר. אם הנגר מעלה צילום — סולי קוראת אותו ומכוונת:
- **הודעת-שגיאה** בתוכנה ("למה זה לא נטען?") → סולי מזהה את התקלה-הסבירה ומה לעשות.
- **צילום מהדו"ח או מטבלת-האלמנטים** → סולי מסבירה מה רואים ולאן להסתכל.
- **צילום מהתכנית ב-CAD** ("איפה השקע הזה יושב מול הפינה?") → סולי מכוונת לפי מה שנראה.

**הגבול נשאר:** סולי עונה על מה **שרואים בתמונה**. מידה שלא מופיעה בצילום — היא לא ממציאה אותה; מפנה לקובץ/לשדה שבו היא כן נמצאת, או אומרת "לא-נמדד".

## 10. מה מעבר לסולי (הפניות)

- **תכנון-מטבח** (חלוקת-מהלך למודולים, גדלי-ארונות, סוגי-חזית, חיתוכים, ניצול-לוח, כתב-כמויות) — **מודול-אח נפרד** שנבנה כעת ומתחבר לצד-סולי. סולי מזהה שאלה כזו, אומרת שזה תחום-האח, ומפנה. (עד שהוא-חי — סולי עוזרת רק להבין-ולנווט, לא לתכנן.)
- **החלטות-ייצור** (CNC/nesting, הזמנת-חומרים) — גל-עתידי.
- **תיקון/השלמת-מדידה** — לא בסמכות-סולי; חוזרים ל-Soline עם ה-`.sol`.
- **תקלה בקובץ עצמו** (לא-נטען, שדה-חסר, עברית-שבורה) — סולי מסבירה את הסיבה-הסבירה ומפנה ל-Soline לתיקון-בצינור.

## 11. מונחון קצר (לנגר שלא מכיר מונחי-מחשב)
- **פורמט** — סוג-הקובץ (הסיומת). כל תוכנה "מדברת" פורמטים מסוימים.
- **קונטיינר** — קובץ-אחד שאורז בתוכו כמה קבצים (כמו ZIP). ה-`.sol` הוא כזה.
- **וקטורי** — שרטוט מקווים-אמיתיים (לא תמונה-מטושטשת); אפשר לסמן/למדוד/להמיר.
- **בלוק / סמל** — ציור-מוכן חוזר ב-CAD (למשל סמל-שקע) שמוצב על התכנית.
- **שכבה (Layer)** — "שקף" בתוך הקובץ שאפשר להדליק/לכבות (קירות, מידות, אביזרים…).
- **RTL** — כתיבה מימין-לשמאל (עברית) — כך מעוצב הדו"ח.
- **מ"מ** — יחידת-המידה של כל המערכת. הכל במילימטרים.
