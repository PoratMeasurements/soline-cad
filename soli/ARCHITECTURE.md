# ARCHITECTURE — איך מגישים את סולי, ואיך היא קוראת פרויקט אמיתי

> איך סולי מגיעה לנגר, ואיך היא עונה על שאלות **ספציפיות-לפרויקט** ("מה רוחב-הדלת בחדר-2?") ולא רק כלליות.

---

## 1. שתי שכבות
סולי = **מוח** (LLM + `system-prompt.md` + `KNOWLEDGE_BASE.md`) + **הקשר-פרויקט** (נתוני החבילה הספציפית שהנגר קיבל). המוח נותן ידע-כללי ("מה זה PDP"); הקשר-הפרויקט נותן תשובות-מספריות ("הדלת בחדר-2 היא 909×2051"). בלי הקשר-פרויקט סולי עונה עקרונית ומפנה לקובץ הנכון; **היא לא ממציאה מספרים**.

---

## 2. אפשרויות-הגשה

### א. צ'אט מוטמע ב-`_report.html` (מומלץ ראשון)
הדו"ח האינטראקטיבי **כבר** נשלח לנגר, עצמאי, נפתח בכל-דפדפן, ומכיל את **כל נתוני-הפרויקט** בתוכו. הטמעת חלונית-צ'אט "שאל את סולי" בפינת-הדו"ח היא ההתאמה הטבעית.
- **יתרונות:** הקשר-הפרויקט כבר בעמוד (אפס-איסוף-נתונים); אותו קובץ שהנגר כבר פתח; אפס-התקנה.
- **חסרונות:** דורש קריאה החוצה ל-LLM (אינטרנט) — הדו"ח עצמו offline אך הצ'אט לא; או הטמעת-מנוע-קטן. צריך מפתח-API.
- **הקשר-פרויקט:** מזריקים לפרומפט את מודל-החדר שכבר מוטמע ב-HTML (טבלת-אלמנטים, מידות, ממצאים) — ראה §3.

### ב. Widget/אתר-Soline
עמוד "סולי" בפורטל-Soline; הנגר גורר/מעלה את החבילה (או את ה-`.sol`/`.pdf`) והצ'אט נפתח מעליה.
- **יתרונות:** מקום-אחד לכל הפרויקטים; קל לעדכן; יכול לקרוא את כל 7 הקבצים ולא רק את ה-HTML.
- **חסרונות:** דורש העלאת-קבצים/התחברות; לא-במקום-העבודה של הנגר (שכבר יש לו את הדו"ח פתוח).

### ג. באפליקציה (app-measure / אפליקציית-נגר עתידית)
צ'אט-סולי בתוך אפליקציית-Soline.
- **יתרונות:** offline-first (קו-המוצר), צמוד-לזרימת-העבודה, גישה-ישירה ל-`.sol`.
- **חסרונות:** האפליקציה היום ממוקדת-מדידה; צ'אט-נגר-על-מכשיר דורש מנוע-LLM (מקומי/ענן) — מאמץ-הנדסי גדול יותר.

### המלצה
**להתחיל מ-(א): צ'אט מוטמע ב-`_report.html`.** הדו"ח כבר בידי-הנגר, עצמאי, ונושא את הקשר-הפרויקט המלא — כך מקבלים תשובות-ספציפיות-לפרויקט מיד עם מינימום-תשתית. אחר-כך להרחיב ל-(ב) פורטל כמאגר-מרכזי, ו-(ג) אפליקציה כשמנוע-LLM-במכשיר יהיה שווה-מאמץ. בכל שלב אותו `system-prompt.md` ואותו `KNOWLEDGE_BASE.md` — משתנה רק **צינור-הקשר-הפרויקט**.

## 3. איך סולי קוראת קובצי-פרויקט אמיתיים (הקשר-פרויקט)

**עיקרון:** אל תשלחו ל-LLM קבצים-בינאריים (PDP/DXF/PDF). שלחו את **המודל-הקנוני** — אותו JSON שהממיר כבר בונה מ-`.sol`/`.ordx`, שכל 6 הפורמטים נגזרים ממנו. הוא קומפקטי, טקסטואלי, ומדויק.

**הצינור:**
```
project.sol  ──►  converter (src/readSol.js / src/parseOrdx.js)  ──►  model (JSON קנוני)
                                                                        │
                              tרימום קל (חדרים/קירות/אלמנטים/מידות/ממצאים)
                                                                        ▼
                          מוזרק לפרומפט של סולי כ"הקשר-פרויקט"  ──►  תשובה עם מספרים ומקור
```

**מבנה המודל (מתוך `converter/docs/README.md` + `REPORT_EXPORTS.md`):**
```
model = {
  job:{name,...}, customer, surveyor, measuredAt, status,
  rooms:[ { name, walls:[ {
      number, dimensions:{length,height,soffit,thick},
      fixtures:[ {name, size:{width,height,depth}, position:{x,y}} ],    // שקעים/חשמל
      furnishings:[ {name, class, type, size:{...}, position:{x,y}} ]     // חלונות/דלתות/הנמכות
  } ] } ],
  findings:[ R1..R10 ], notes, summary:{ itemCounts, ... }
}
```
כל שדה שסולי מצטטת בא **משם** — ולכן היא יכולה לומר "לפי המדידה, הדלת בקיר-3 היא 909×2051" **עם מקור**, ולומר "לא-נמדד" כשהשדה `—`/חסר.

**מה מזריקים בפועל (מומלץ, כדי לחסוך-טוקנים ולמנוע-הזיה):**
1. סיכום-פרויקט: שם-עבודה, מודד, תאריך, סטטוס, ספירת-חדרים/אלמנטים.
2. לכל חדר: רשימת-קירות עם מידות, וטבלת-אלמנטים (סוג/מידות/מיקום/כיוון/סף).
3. הממצאים R1–R10 וההערות.
4. **מטא-דאטה של איזה-קובץ-מכיל-מה** (כדי שסולי תוכל להפנות: "ה-DXF-2D יראה לך את זה בתכנית").

**כלל-זהב ל-grounding:** סולי עונה מספרים **רק** מהקשר-הפרויקט המוזרק או מ-`KNOWLEDGE_BASE.md`. אין ערך בהקשר → "לא-נמדד"/"לא-בחבילה". זה מה שמונע-הזיה. ה-`system-prompt.md` כבר אוכף זאת.

## 3א. קלט-תמונה (multimodal) — צילום-מסך כערוץ-שני

חלק גדול מתקלות-הנגר מתוארות הכי-טוב **בתמונה**: הודעת-שגיאה בתוכנה, פינה בתכנית-CAD, שורה בטבלת-האלמנטים. אם מנוע-ה-LLM שנבחר תומך-ראייה (רוב המנועים המובילים כן) — מאפשרים לנגר **לצרף צילום-מסך** לצ'אט.
- **מתי זה מנצח טקסט:** אבחון "למה זה לא נטען", "לאיזה צד יושב השקע הזה", "מה כתוב כאן בדו"ח".
- **הגבול נשמר:** סולי עונה על מה שנראה בתמונה; מידה שלא בתמונה — לא מומצאת (אותו כלל-grounding של §3, מורחב לתמונה). ה-`system-prompt.md` כבר אוכף זאת.
- **מימוש:** בערוץ (א) — קלט-קובץ/הדבקה-לצ'אט בחלונית-הדו"ח; התמונה נשלחת ל-LLM לצד הקשר-הפרויקט הטקסטואלי.

## 3ב. פרטיות והקטנת-מידע (PII)

סולי לרוב קוראת החוצה ל-LLM בענן — לכן **ממזערים מידע-מזהה** של הלקוח:
- **הקשר-הפרויקט המוזרק** (§3) הוא מודל-מדידה גיאומטרי — קירות/אלמנטים/מידות/ממצאים. מזה **משמיטים** שדות-לקוח מזהים (שם-מלא, כתובת, ת"ז, טלפון, סכומים): הם לא נחוצים לניווט/הבנת-קבצים.
- **לא שולחים בינאריים** (כבר החלטה קיימת) — וזה גם מקטין דליפת-מטא-דאטה.
- ה-`system-prompt.md` מנחה את סולי לא לבקש פרטים-מזהים ולהעיר בעדינות אם הנגר מדביק כאלה.

## 3ג. פרופיל בית-המלאכה (onboarding חד-פעמי, אופציונלי)

כדי שסולי תתאים-אישית מהרגע-הראשון ולא תחזור על שאלות — אפשר לשמור **פרופיל-נגר קטן** ולהזריקו כהקשר-קבוע:
```
workshopProfile = { plansIn: "raumplan" | "cad" | "paper" | "ordx-kitchen",
                    cadTool?: "AutoCAD" | "LibreCAD" | ...,
                    hebrewUI?: bool, notes?: "..." }
```
עם פרופיל כזה סולי מדלגת על "במה אתה מתכנן?" ומכוונת ישר לקובץ/לתוכנה הרלוונטיים. בלי פרופיל — היא שואלת פעם-אחת בהכרות (ראה `PERSONA.md` §onboarding) ומתאימה משם. זהו **הקשר** נוסף, לא מוח-נוסף — אותו `system-prompt.md`.

> **הערה עקרונית:** סולי היא **עוזר-מוגדר-קבוע** (system-prompt + KB + הקשר-מוזרק), לא צ'אט-ריק שמלמדים מחדש בכל פעם. זה בדיוק ההבדל בין הסבר-מאפס בכל שיחה לבין עוזר שכבר "מכיר" את המערכת ואת בית-המלאכה.

## 4. תכנון-מטבח — כמה יכולת (plug-in), לא מוח-נפרד
מודול-תכנון-המטבח (**סוכן-אח**, בבנייה) מתחבר כ**יכולת** לצד סולי, לא כמוח-מתחרה:
- **הפרדת-אחריות:** סולי = הבנה-וניווט (read-only, מסבירה); מודול-התכנון = ייצור-תכנון (חלוקת-מהלך, מודולים, חיתוכים, ניצול-לוח).
- **הקשר-משותף:** שניהם צורכים את **אותו מודל-קנוני** מה-`.sol` (§3). אין כפילות-נתונים.
- **ניתוב:** סולי מזהה כוונת-תכנון ומעבירה למודול-התכנון (או מסמנת שהוא-בבנייה). מודול-התכנון יכול לחזור לסולי לשאלות-הבנה על הקבצים.
- **מימוש טכני:** בארכיטקטורת-כלים (tool/function-calling), תכנון-המטבח הוא `tool` שסולי (או שכבת-ניתוב מעליה) קוראת-לו. אותו `system-prompt.md` נשאר; רק נוסף כלי.
- מקורות-רקע לתכנון (בריפו, לא לסולי-עצמה): `converter/docs/kitchen_layout_fitting.md`, `REPORT_EXPORTS.md` §PLANNING (סכמת-ארונות ב-`.sol`).

## 5. סיכום-החלטות
| החלטה | בחירה |
|---|---|
| הגשה ראשונה | צ'אט מוטמע ב-`_report.html` |
| הרחבה | פורטל-Soline → אפליקציה |
| הקשר-פרויקט | המודל-הקנוני (JSON) מהממיר — לא קבצים-בינאריים |

| תכנון-מטבח | סוכן-אח כ-plug-in/tool, הקשר-משותף |
| עקביות בין-ערוצים | אותו system-prompt + KB בכל הגשה |
