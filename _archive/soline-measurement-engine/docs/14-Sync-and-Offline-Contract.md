# 14 · חוזה הסנכרון והאחסון המקומי-תחילה (Session 3)

> **סטטוס:** מפרט לבנייה — *Session 3*.
> **כלל-על:** אין מימוש לוגיקה עסקית. זהו החוזה המדויק של שכבת ה-offline-first.
> **מדוע עכשיו:** offline-first הוא דרישה עקרונית ([ADR-002](09-ADRs.md)). ליבת האימות
> ([מסמך 13](13-Validation-Core-Spec.md)) רצה על-גבי-ההתקן — חוזה זה מגדיר כיצד התוצאות
> נשמרות מקומית ומסונכרנות בבטחה, ללא אובדן נתונים וללא מיזוגים שקטים.

---

## 1. עקרונות

1. **מקומי-תחילה (local-first):** לקוח השדה כותב תמיד לאחסון מקומי; הסנכרון הוא אסינכרוני.
   האחסון המקומי הוא מקור האמת **עד** הסנכרון; ה-backend סמכותי **אחרי**.
2. **מזהים נוצרים-בלקוח:** כל ישות מקבלת UUID בצד הלקוח → אין התנגשות מזהים, אין המתנה לשרת.
3. **קריאות הן append-only:** ולכן **חסרות-קונפליקט** מטבען. תיקון = קריאה חדשה + קישור
   `superseded_by`. זה מסלק ~90% מהקונפליקטים.
4. **אידמפוטנטיות בכל מוטציה:** שליחה חוזרת (רשת רעועה) בטוחה לחלוטין.
5. **אין אובדן שקט:** כל מוטציה שלא יושמה חוזרת כ**קונפליקט מפורש** — לעולם לא נמחקת בשקט.
6. **בני-אדם מכריעים במקרים הקשים:** קונפליקט של פקודה (למשל שתי הכרעות GO/NO-GO) מוצג
   למפעיל; המערכת לעולם אינה ממזגת שתי החלטות אוטומטית.

---

## 2. האחסון המקומי (local store)

```ts
// מראה מקומית (SQLite / WatermelonDB) של ההיקף שהוקצה למכשיר.
interface LocalStore {
  entities: {                    // עותק מקומי של הישויות בהיקף
    readings; measurements; crossValidationSets; validationResults;
    projects; readinessChecks; goNoGoDecisions; geometry;
  };
  mutationLog: Mutation[];       // §3 — יומן שינויים ממתין לסנכרון
  cursor: string;                // סמן ה-delta האחרון שהתקבל מהשרת
  scope: { orgId: string; projectIds: string[] };  // מה המכשיר רשאי להחזיק
}
```
- ההיקף (`scope`) מוגבל לארגון + פרויקטים שהוקצו למכשיר — לא כל בסיס הנתונים.
- כל הכתיבות עוברות דרך יומן המוטציות; ה-UI קורא מהמראה המקומית (קריאה מיידית, ללא רשת).

---

## 3. יומן המוטציות (mutation log)

```ts
interface Mutation {
  clientMutationId: string;      // UUID — מפתח האידמפוטנטיות
  seq: number;                   // סדר מקומי מונוטוני בתוך המכשיר
  op: 'create' | 'command';      // create=ישות חדשה · command=מעבר מצב
  entity?: EntityKind;           // ל-create
  commandName?: string;          // ל-command (למשל 'decideGoNoGo')
  payload: unknown;
  baseVersion?: string;          // ל-command: גרסת המצב שכנגדה הופקה הפקודה (§6)
  localTs: string;               // חותמת מקומית — לתצוגה בלבד, לא לסמכות
}
```
- **`create`** לישויות (readings, measurements). קריאות תמיד מתקבלות (append-only).
- **`command`** למעברי מצב (GO/NO-GO, סיום session). נושא `baseVersion` לבדיקת תנאי-קדם.
- **`localTs` אינו סמכותי** — הסמכות היא סדר הקבלה בשרת (מונע בעיות סחף שעון).

---

## 4. פרוטוקול הסנכרון

נקודת קצה אחת, דו-כיוונית: דוחפת מוטציות, מושכת delta.

```http
POST /v1/orgs/{orgId}/sync
Idempotency-Key: <batch-uuid>
```
```ts
interface SyncRequest {
  clientId: string; deviceId: string;
  cursor: string;                // הסמן האחרון שהמכשיר מחזיק ('0' בהתקנה טרייה)
  mutations: Mutation[];         // מסודרות לפי seq
}
interface SyncResponse {
  applied: string[];             // clientMutationIds שיושמו
  conflicts: Conflict[];         // §6 — מה שלא יושם ומדוע
  serverChanges: EntityDelta[];  // שינויים שהמכשיר לא החזיק (כולל re-validation)
  cursor: string;                // סמן חדש לשמירה
}
interface Conflict {
  clientMutationId: string;
  reason: 'precondition-failed' | 'superseded' | 'validation-divergence' | 'out-of-scope';
  current: unknown;              // המצב הסמכותי הנוכחי — כדי שהמפעיל יכריע מחדש
}
```
- **באצ׳:** מוטציות רבות בבקשה אחת; כישלון של אחת אינו חוסם את השאר.
- **סמן (cursor):** watermark מונוטוני בצד השרת (רצף/גרסה) — לא חותמת-זמן לקוח.
- **מנוחה נקייה:** בקשה חוזרת עם אותו `Idempotency-Key` מחזירה את אותה תוצאה.

---

## 5. אידמפוטנטיות וניסיונות חוזרים

- כל `clientMutationId` נרשם בשרת בטבלת דה-דופ. מוטציה שכבר יושמה → מוחזרת כ-`applied` שוב,
  ללא כפילות.
- ה-batch כולו נושא `Idempotency-Key` — שליחה חוזרת של batch שלם בטוחה.
- הלקוח מוחק ממוטציה מהיומן רק לאחר שהתקבלה ב-`applied` (או הוכרעה כקונפליקט).

---

## 6. טקסונומיית קונפליקטים ומדיניות היישוב

| ישות | קונפליקט אפשרי? | יישוב |
|---|---|---|
| **Reading** | לא (append-only) | תמיד מתקבל. תיקון = reading חדש + `superseded_by`. |
| **Measurement** | נדיר | מגורסא; עריכות מקבילות — שתיהן נשמרות, ה-current נקבע לפי סדר סיבתי; המפסידה נשמרת בשושלת. |
| **Command (GO/NO-GO, סיום)** | כן — המקרה הקשה | ראו למטה. |
| **Geometry revision** | כן | רוויזיות מסתעפות; גאומטריה נעולה בלתי-משתנה (I-G3); השרת מיישב לפי שושלת רוויזיות. |

**פקודות — הכלל המרכזי:** כל `command` נושא `baseVersion` = גרסת מצב הפרויקט שכנגדה הופקה.
בשרת:
1. אם `baseVersion` == הגרסה הנוכחית → הפקודה מיושמת, הגרסה מתקדמת.
2. אם המצב השתנה בינתיים (מכשיר אחר הקדים) → הפקודה **נדחית** ומוחזרת כ-
   `conflict{ reason:'precondition-failed', current }` — **לא** מיושמת ולא ממוזגת.
3. המפעיל רואה את המצב הסמכותי הנוכחי ומכריע מחדש (הכרעה חדשה = פקודה חדשה).

> כך "שתי הכרעות GO/NO-GO offline" לעולם אינן ממוזגות בשקט: הראשונה-התקפה קובעת, השנייה הופכת
> לקונפליקט גלוי. עולה בקנה אחד עם ADR-008 (GO/NO-GO בלתי-ניתן-לשינוי, פולט-אירועים).

---

## 7. אימות חוזר סמכותי בעת סנכרון

- עם קבלת מדידות, ה-backend **מריץ מחדש את ליבת האימות** ([מסמך 13](13-Validation-Core-Spec.md))
  באופן סמכותי — הוא רואה נתונים חוצי-sessions/מכשירים שההתקן הבודד לא ראה.
- אם התוצאה הסמכותית חמורה מזו שעל-גבי-ההתקן → מוחזרת ב-`serverChanges` עם
  `reason:'validation-divergence'`, ונרשם אירוע `ValidationDivergence`. **לעולם לא מוסתר.**
- ההתקן מעדכן את המראה המקומית מ-`serverChanges`.

---

## 8. אבטחה והיקף

- כל בקשה מוגבלת-ארגון ומאומתת; מכשיר מקבל delta רק עבור ה-`scope` שלו.
- מדיה כבדה (תמונות אתר; ובעתיד ענני-נקודות) **אינה** עוברת ב-JSON — היא עולה ישירות
  לאחסון-אובייקטים דרך **pre-signed URL**, והמוטציה נושאת `blobRef` בלבד.
- מכשיר שאבד → ניתן לשלול את ה-scope שלו; הנתונים המקומיים מוצפנים במנוחה.

## 9. תרחישי קבלה (המימוש חייב לעבור אותם)

| # | תרחיש | פלט צפוי |
|---|-------|----------|
| ST-1 | יצירת readings+measurements offline → sync | הכול `applied`, מזהי הלקוח נשמרים |
| ST-2 | שליחת אותו batch פעמיים (retry) | אידמפוטנטי — ללא כפילות |
| ST-3 | שני מכשירים מכריעים GO/NO-GO offline על אותו פרויקט | הראשון-התקף `applied`; השני `conflict:precondition-failed` + current |
| ST-4 | תיקון קריאה (`superseded_by`) | שתי הקריאות נשמרות, השושלת שלמה |
| ST-5 | אימות חוזר מוריד PASS(on-device)→FAIL(backend) | `serverChanges` עם `validation-divergence` + אירוע |
| ST-6 | batch עם פקודה פסולה אחת | השאר `applied`, הפסולה ב-`conflicts` |
| ST-7 | סחף שעון בלקוח | הסמכות היא סדר הקבלה בשרת, לא `localTs` |
| ST-8 | מדיה גדולה | עולה דרך pre-signed URL; המוטציה נושאת `blobRef` בלבד |
| ST-9 | התקנה טרייה / מכשיר חדש (cursor='0') | משיכה מלאה של ה-scope |
| ST-10 | ניתוק ארוך ואז סנכרון | כל היומן מיושם בסדר, ללא אובדן |

## 10. Definition of Done

1. אחסון מקומי משקף את ה-scope; יומן מוטציות עמיד (שורד קריסה/הפעלה מחדש).
2. `/sync` מממש את חוזה הבקשה/תשובה; אידמפוטנטי; חושף קונפליקטים.
3. **אפס אובדן נתונים שקט** — כל מוטציה שלא יושמה חוזרת כקונפליקט.
4. פקודות נדחות על תנאי-קדם שנשבר ומוחזרות עם המצב הנוכחי (ללא מיזוג).
5. ה-backend מאמת מחדש; divergences נרשמים ומוחזרים.
6. כל 10 תרחישי הקבלה (§9) עוברים.

> **עדיין ללא לוגיקה עסקית מיושמת** — זהו המפרט. הבנייה מתחילה עם אישור המפרטים.
